# services/api

Express 5 modular monolith. Package name: `@onemarketplace/api`. ESM; import across directories with `@/` (the `src` root) and siblings with `./`, always with `.js` suffixes; `../` is not allowed (`docs/decisions/0020-import-aliases.md`). The tutorial code was migrated here (`docs/decisions/0003-api-migration.md`). The code is the product source of truth: read a module fully before changing it.

## Layout

Source layout and import rules: `docs/decisions/0013-api-source-layout-and-import-boundaries.md`. To add a module or route, follow `docs/adding-an-api-module.md`.

- `src/modules/<name>/`: one folder per domain with the folder layout below; `index.ts` only where another module needs it (agency, auth, connects, freelancer, health, jobs, messaging, payouts, proposals; `contracts/index.ts` exports only the refund reconciliation cron entry points for bootstrap).
- `src/modules/contracts/` is the reference for a split module: use-case services in `services/` (`contracts.checkout`, `listing`, `lifecycle`, `milestones`), tests in `tests/`. The controller imports the specific service file; there is no barrel. `contracts.repository.ts` holds plain exported functions that take a `DbExecutor` (`database/database.types.ts`, a db or a transaction) as the first argument: the long single-use lookups and the listing query. `contracts.state.repository.ts` holds the `FOR UPDATE` locks and the guarded updates and inserts whose WHERE or conflict clause encodes a state guard (`markMilestoneFundedIfPending`); they return rows or counts and carry no `ApiError`. Message, last-message and unread writes go through `appendConversationMessages` in `messaging/index.ts`. Services keep transactions, the order of calls and the interpretation of results, and pass the transaction handle down. A repository exists only when ADR 0014 thresholds are met; no classes, no pass-through wrappers.
- `src/infrastructure/`: one folder per third-party service (`auth/`, `cache/`, `events/`, `payments/`, `storage/`, `video/`) plus shared `constants/`, `types/` (each with an `index.ts` barrel) and `utils/` (`*.utils.ts`); every client file is `<service>.client.ts` (Stripe, Clerk, Daily, ImageKit, Redis, RabbitMQ) and `events/` also holds `notification.{envelope,topology,publisher}.ts` (ADR 0004). Use `import type` for type-only imports. `src/test/architecture/infrastructure-layout.test.ts` enforces the layout (ADR 0013). The consumer is `modules/notifications/notifications.consumer.ts`.
- `src/middleware/`: one folder per middleware (`error/`, `not-found/`, `request-id/`, `http-logger/`, `validate/`, `json-body/`, `rate-limit/`, `auth/` with the admin-session and role guards), each holding the middleware and its test, plus `constants/`, `types/` and `utils/` for extracted owner-named files (`*.constants.ts`, `*.types.ts`, `*.utils.ts`, including `async-handler.utils.ts`). Modules, bootstrap and infrastructure import it; it never imports modules (ADR 0014). `src/test/architecture/shared-layout.test.ts` enforces the layout.
- Rate limiters (`middleware/rate-limit/`) share a Redis store (`middleware/utils/redis-rate-limit-store.utils.ts`): keys `rl:<limiterName>:<key>`, one Lua script for INCR and PEXPIRE, and an in-memory fallback with a `rate_limit.store.error` warning (at most once per minute) when Redis fails. Every limiter instance needs its own stable name.
- `src/shared/`: `errors/` (`api-error.ts`), `responses/` (`api-envelope.responses.ts`, `scalar.responses.ts`), `validation/` (`schemas/` with `common.schema.ts`, `country.schema.ts`, `pagination.schema.ts`, `search.schema.ts`, `money.schema.ts`; `constants/` with `validation.constants.ts` and the limits shared by several modules; `utils/` with `email.utils.ts`, `pagination.utils.ts`, `require-text.utils.ts`), `money/money.ts`, `logging/` (`sanitize-log.ts`), `uploads/` (`attachments.ts`, `portfolio-images.ts`, `storage-paths.ts`, `upload-documents.ts` with `constants/`, `types/`, `utils/`), `ids/` (`public-ids.ts`, `uuid-v5.ts`), `search/` (`search-text.ts`: `buildSearchText`, `countryDisplayName`; `search-terms.ts`). There is no `shared/http`.
- `src/config/`: validated env, cors, pino logger, and `constants.ts` (API prefix, service name, webhook paths). Configuration only: domain constants, validators and cache keys live with their owner (Connects plans and keys in `connects`, the earnings hold in `payouts`, `PLATFORM_FEE_BPS` in `shared/money/money.ts`, `requireText` in `shared/validation/utils/require-text.utils.ts`, Stripe payout countries in `infrastructure/constants/`, the account-auth cache keys in `infrastructure/utils/`).
- `src/bootstrap/`: ordered start, shutdown, crash handlers and readiness. Start checks the database, listens, then starts the consumer, socket, payout cron and refund reconciliation cron; shutdown stops both crons and awaits in-flight payout and reconciliation runs before closing the pool. `src/routes/`: route assembly only (`index.ts`).
- `src/database/`, `drizzle/`, `drizzle.config.ts`: `client.ts` (no schema argument; the pool has an `error` listener and the limits named in `database.constants.ts`), `database.types.ts` (`DbExecutor`), `pg-errors.ts` (`isUniqueViolation(error, constraintName)` for SQLSTATE 23505), generated migrations, config. `database/` imports no module file. Tables and enums live in the owning module as `modules/<name>/models/<name>.model.ts` (drizzle; the zod request schemas are `schemas/<x>.schema.ts`), found by the glob in `drizzle.config.ts`. A table file imports only drizzle-orm and other table files; controllers and routes never import one (ADR 0014 section 9, ADR 0016). Tests import tables through `src/test/support/tables.ts`.

## Module folder layout

Every module under `src/modules/<name>/` follows `docs/decisions/0016-module-folder-layout.md`, enforced without exemptions by `src/test/architecture/module-layout.test.ts`:

- Root: only `<name>.route.ts`, `index.ts` and the entry points `<name>.socket.ts`, `<name>.cron.ts`, `<name>.consumer.ts`.
- Folders (created only when they hold files, never nested): `controllers/` (`*.controller.ts`), `services/` (`*.service.ts`, plus `*.sse.ts`), `repositories/` (`*.repository.ts`), `models/` (only `<name>.model.ts`), `schemas/` (`*.schema.ts`), `responses/` (`*.responses.ts`), `middleware/` (`*.middleware.ts`), `tests/` (`*.test.ts`), `types/` (`*.types.ts`), `constants/` (`*.constants.ts`), `utils/` (other helpers such as `agency.errors.ts`, `payouts.state.ts`, `earnings-certificate.pdf.tsx`).
- `models/<name>.model.ts` is drizzle (tables and enums); `schemas/<x>.schema.ts` is zod request schemas. A role-suffixed file in any other folder fails the test.

## Rules

- A module may not read or write another module's tables unless the edge is in `src/test/architecture/table-access-allowlist.ts`; the allowlist type holds reads only and a detected write fails the test, so a write to another module's table is an owner function in the owner's `index.ts`. New read edges need review; `table-access.test.ts` enforces this. `models/<name>.model.ts` (drizzle tables) is not `schemas/<x>.schema.ts` (zod request schemas).
- SQL lives in `repositories/<module>.repository.ts` files (ADR 0015): outside `database/`, `bootstrap/`, tests, `*.model.ts` and repositories, no file may import `drizzle-orm` query helpers or a `*.model.ts`, or call `select`, `insert`, `update`, `delete` or `execute` on `db`, a transaction or an executor. A service may import `db` only to open `db.transaction`. `index.ts` files only re-export. Every module is converted and there is no exemption list: `repository-sql.test.ts` fails on any file that breaks the rule. A repository holds SQL only: no `ApiError`, no `throw`, no non-SQL I/O (`repository-purity.test.ts`); it returns data or a result and the service interprets it and throws. A thin service that only supplies `db` to a repository function is acceptable.
- A public function that another module calls inside its transaction takes the executor first, does SQL only, and leaves sockets, notifications, Redis and cache invalidation to the caller after commit (ADR 0014 section 11).
- Searchable text (ADR 0019): `accounts.display_name` and `avatar_url`, `freelancer_metadata.search_text` and `location_text`, and `agency_metadata.search_text` are written in the owner's write path with `buildSearchText`, never by trigger. Call `syncAccountDisplay` (auth `index.ts`) before, never inside, a transaction; it never throws. `scripts/backfill-search-text.ts [--dry-run]` rebuilds them. List and profile paths read names and avatars with `findAccountDisplays` (auth `index.ts`, one batched query, no Clerk) and fall back to their placeholder when a name is null; never add a per-row Clerk lookup. Other modules map Clerk ids to public account ids with `findAccountPublicIds(executor, authIds)` (auth `index.ts`), never their own `accounts` query. The client country is `client_metadata.country`, validated with `countryCodeSchema` (`shared/validation/schemas/country.schema.ts`).
- Job feeds (ADR 0022): the freelancer and agency feeds run in SQL, two queries per page (ids with the best-match score, then the page rows with counts), never a whole-table load. Best-match reads `job_posts.content_norm`, a stored generated column. Selects that feed responses use `jobPostColumns` (`jobs/index.ts`), which leaves it out, and `toJobPostResponse` drops it too; never return it. `docs/frontend-integration-notes.md` lists the frontend consequences of API behavior; update it when a response shape or status changes.
- Third-party clients are created only in `src/infrastructure/` (eslint enforces it). Modules import them from there. The Stripe, Clerk and ImageKit clients are lazy (`createLazyClient`), so importing them never constructs the SDK.
- A module imports only `config`, `infrastructure`, `shared`, `database` and lower-layer modules, and only through the other module's `index.ts`, never its controller or internals. Do not write tables you do not own (ADR 0013). `src/test/architecture/import-boundaries.test.ts` enforces this; its exception list stays empty, cycles are never allowed, and no file inside a module imports its own `index.ts`. Table definition files (`*.model.ts`) are exempt from the boundary and layer rules; cross-module table reads are governed by the table-access allowlist instead.
- Validate every body, query and param with zod at the route boundary (ADR 0011):
  - Every route uses `validate({ params, query, body })` from `src/middleware/validate/validate.middleware.ts`, placed after authentication and role middleware.
  - `validate` records the parsed input on the request. A controller reads it only through `getValidated(request, <schemas>)` (`src/middleware/utils/validated-request.utils.ts`), typed with `z.infer` of the schemas; no `request.body`, `request.params` or `request.query` read and no per-field cast. The schemas object (`<route>Request`, `{ params, query, body } satisfies RequestSchemas`) is defined once in `schemas/<x>.schema.ts` and the route spreads the same constant into `validate({ ...<route>Request, responses })`. `src/test/architecture/controller-input.test.ts` enforces it; its only exception is the Daily raw-body webhook.
  - Schemas live in `src/modules/<name>/schemas/<x>.schema.ts`. Limits are defined only in `constants/<module>.constants.ts` of the owning module, or in `src/shared/validation/constants/` when several modules use them; no inline numbers for lengths or counts.
  - Every `:id` param uses `uuidParam` or `uuidParams` from `src/shared/validation/schemas/common.schema.ts`.
  - Objects are strict. Do not add a route without validation unless it is listed in `src/test/architecture/routing/validation-allowlist.ts` with a written reason. The registry test enforces this.
- Every route declares request and response schemas: `validate({ params, query, body, responses })` with a 2xx entry in `responses` (schemas in `responses/<name>.responses.ts`, shared ones in `src/shared/responses/api-envelope.responses.ts`), and has a contract test that parses real responses with them. Only raw-body webhooks and event streams are exempt, listed with a reason in `src/openapi/introspection/contract-allowlist.ts`. Run `pnpm --filter @onemarketplace/api openapi:generate` and commit the regenerated `docs/api/openapi.json`; CI fails on drift (ADR 0012).
- Money is always integer cents, never floats: `bigint` `*_cents` columns, `*Cents` API and JSON fields, no `toFixed`, `/ 100` or `Math.round(x * 100)` on money. Use `splitFee`, `toSafeCents`, `moneyCents` and `formatUsd` from `src/shared/money/money.ts`; shared zod pieces are in `src/shared/validation/schemas/money.schema.ts` (ADR 0006).
- API request and response fields are lowerCamelCase and domain enum values are UPPER_SNAKE; `src/openapi/tests/openapi-naming.test.ts` enforces the field names.
- Controllers may not import `infrastructure/**` or `config/env`; ESLint enforces it. A caller with no agency is answered by `requireAgencyId` or `requireAgencyIdWithPermission` (`agency/index.ts`): 404 "No agency workspace was found for this account.", never 403; a missing permission stays 403 (ADR 0021).
- Daily rooms are private; a join URL is the stored room URL plus a per-user meeting token from `createMeetingJoinUrls` (`messaging/index.ts`) with the public `accounts.id` as `user_id`, never a Clerk id, minted per request and never stored (ADR 0021).
- Read configuration only through the config module. Never hardcode secrets or URLs.
- The API never returns Clerk ids (`accounts.auth_id`). The public person id is `accounts.id` and the agency id is `agency_metadata.id`; repositories return the Clerk id for internal use and the uuid for responses, and `requirePublicId` (`src/shared/ids/public-ids.ts`) turns an unresolved uuid into a logged 500 `INTERNAL_ERROR`, never a Clerk-id fallback. Storage folders (message, job, portfolio uploads) use `accounts.id` or `agency_metadata.id` through `src/shared/uploads/storage-paths.ts`, never a Clerk id. Messaging socket payloads (`presence:snapshot`, `presence:update`, `typing:update`, `conversation:update`) and admin responses use the same public ids; rooms, `userSockets` and cache keys keep Clerk ids internally. The one exception is `authId` on `GET /admin/accounts`; `openapi-clerk-ids.test.ts` guards every other operation (ADR 0012).
- Error responses are `{ success: false, message, code, requestId, errors? }`. Never return stack traces, SQL errors or internal messages for 5xx.
- Pagination (ADR 0012): offset lists take `limit` (integer, default 20, 1 to 100) and `offset` (integer, default 0, 0 to 10000) from `paginationQuerySchema` in `src/shared/validation/schemas/pagination.schema.ts` and return `data: { results, hasMore }` (`offsetPage`), computing `hasMore` by fetching `limit + 1` rows (`fetchSize`, `toOffsetPage`); cursor lists take `cursor` and an integer `limit` and return `data: { results, nextCursor }` (`cursorPage`); the messages list is the one documented exception on limit numbers (default 30, max 50). Every paginated query ends its ORDER BY with the primary key. The one exemption is `GET /admin/system/redis/keys` (a SCAN hard-capped at 200 keys, `{ keys, truncated }`); `src/openapi/tests/openapi-pagination.test.ts` lists it by id and fails on any other list operation that is unpaginated or answers a bare array.
- No `console.*`; use the pino logger.
- Webhook routes need the raw body, registered before `express.json`. The Daily webhook validates the parsed body with `dailyWebhookEventSchema` and answers 400 "Invalid Daily webhook payload." (ADR 0021). Stripe webhook controllers verify the signature with `verifyStripeWebhook` (`infrastructure/payments/stripe.webhook.ts`) and keep their own messages.
- RabbitMQ is optional; the API must start and work with only Postgres and Redis. It is enabled by `RABBITMQ_URL`.
- Job and payment flow: the payment webhook creates the contract and sets the job HIRED in one transaction (`markJobHired`, jobs owner); a HIRED job answers 409 `JOB_LOCKED` on edit and delete. Duplicate paid sessions are refunded with `refundDuplicatePayment`; paid sessions that permanently cannot be fulfilled (missing offer, invalid milestones, mismatch, unfundable milestone) with `refundUnfulfillablePayment` and a 200; transient failures still throw so Stripe retries (ADR 0008, M2). In those webhook refunds a permanent Stripe error (`charge_not_refundable`, `refund_disputed_payment`, `resource_missing`) is logged as `payment.refund.unrecoverable` and answered with 200, any other error rethrows (500), and a payment intent missing from the event is read once from the Checkout Session, else `payment.refund.no_payment_intent` and a 500; alert on both log names (ADR 0008, update 2026-11-19). A talent can decline (`PATCH /contracts/:contractId/decline`) and the client can withdraw (`PATCH /contracts/:contractId/withdraw`) a `PENDING` contract: the contract becomes `CANCELLED` and the job returns to `PUBLISHED` through `releaseJobHire` in one short transaction, then the first payment is refunded outside it; repeating the call repairs a failed refund (ADR 0007, item c). The cancel facts (`cancelled_at`, `cancelled_by`) are set in the cancelling `UPDATE` and the refund result (`refunded_at`, `refund_id`) by one guarded update after a successful refund; only the call that records `refunded_at` emits and notifies, so a repeat after a failed refund notifies once and a repeat after a successful one sends nothing (ADR 0007, update 2026-11-19). The retry state of a cancelled, unrefunded contract is `refund_attempts` (0 to 20, default 0), `refund_next_attempt_at` (lease or backoff time) and `refund_last_error` (short code); `reconcileCancelledContractRefunds` (`contracts.refund-reconciliation.service.ts`) reads and writes them; `contracts.cron.ts` runs it every 15 minutes in the mode of `REFUND_RECONCILIATION_MODE` (`off`, `detect` default, `on`) (ADR 0007, update 2026-11-19, reconciliation; ADR 0023). `CANCELLED` is neither ongoing, completed nor payable.
- The RabbitMQ connection is created at startup by `src/bootstrap/start.ts`; new entry points that publish must start it first.
- Redis is configured with `REDIS_URL`.
- Extend `@onemarketplace/tsconfig/node.json` and `@onemarketplace/eslint-config/node`.
- Schema changes and migrations go only through `/db-change`, against the local Docker database. Never run migrations against Neon or any remote database.
- A test that writes PAID `payout_history` rows or reads global payout totals must be added to the `payout-totals` project in `vitest.config.ts`. So must a test that asserts on global row counts or on the page order of search results over rows other test files write (`client.contract.test.ts`): the project runs after the parallel one, so no concurrent file changes those rows.

## TypeScript conventions

- `interface` for object contracts, DTOs, configuration objects and extensible object structures; `type` for unions, intersections, primitive aliases, function signatures, mapped and conditional types, utility compositions and `z.infer` / `typeof` / `$inferSelect` aliases. `@typescript-eslint/consistent-type-definitions` enforces it; a declaration that must stay a `type` carries a narrow `eslint-disable-next-line` with a reason (ADR 0018).
- Database-specific types live in `src/database/database.types.ts` and are imported with `import type`.
- No new explicit `any`, non-null assertions, narrowing `as` assertions or `@ts-ignore`; `@ts-expect-error` needs a one-line reason.
