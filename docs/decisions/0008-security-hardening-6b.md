# 0008: Security hardening 6b

Status: accepted (Stage 6b). Fixes the findings of the Stage 6a audit of `services/api` that were selected for this stage. Extends ADR 0007 (guarded transitions) for invitation accept.

## Context

The 6a audit was a read-only review of `services/api`. It found no classic IDOR (every `:id` route filters by the caller) but several trust and integrity gaps. This stage fixes a selected subset with one small change per finding. Money, agency role permissions, rate-limit storage and route-wide zod are out of scope (see "Remaining findings").

### Side effect to know about

`createUserRateLimiter` keyed on `authClaims`, which only `verifyBearerToken` sets; `isAuthenticated` sets `request.auth` instead, so a user limiter behind `isAuthenticated` fell back to per-IP. It now keys on `request.auth.userId`, then `authClaims`, then IP (the same Clerk subject). The existing user limiters (jobs, agency profile, messaging writes) sit behind `verifyBearerToken` and behave as before; the change matters for the new invite limiter, which sits behind `isAuthenticated`.

The pending invitations list (`GET /agency/team/invitations`) no longer returns an avatar (`avatarUrl` is always `null`), because the avatar was only present for registered emails and revealed registration.

## M2: duplicate and mismatched payments, HIRED lock

- Job lock: `createContractFromPayment` calls `markJobHired` (jobs module, exported from `modules/jobs/index.ts`) right after the contract insert in the same transaction. No row means another contract hired the job or it is not PUBLISHED: the transaction rolls back and the payment is refunded. A job is single-hire.
- Proposal: `markProposalHired` (proposals module, `modules/proposals/index.ts`) runs in the `acceptContract` transaction and only changes an INTERVIEWED proposal. The freelancer dashboard counts HIRED as active.
- Checkout: `createContractCheckout` answers 409 `CONTRACT_EXISTS` when the proposal already has a contract and 409 `JOB_ALREADY_HIRED` when its job is HIRED. New sessions (contract and milestone funding) expire after 35 minutes (Stripe allows 30 minutes to 24 hours) and carry `client_reference_id` (the proposal or milestone id). Session creation has no idempotency key.
- Refunds: `refundDuplicatePayment` calls `stripe.refunds.create({ payment_intent, reason: "duplicate" }, { idempotencyKey: "refund:<paymentIntentId>" })`. A failure is logged (`payment.refund.failed`) and rethrown so Stripe retries the webhook; a `charge_already_refunded` error counts as done. `refundUnrecordedPayment` refunds only when no milestone stores this session id, so a replay of the winning webhook never refunds the winner. Refunds run outside the database transaction.
- Refund causes: a second session for the same proposal or an already funded milestone (`duplicate_session`), a job that is not PUBLISHED at webhook time (`job_already_hired`), and an amount, currency or customer that differs from the job's current first milestone or the milestone amount (`amount_mismatch`, logged as `payment.mismatch` with the session id and amounts). The webhook then answers 200 instead of 400, so Stripe stops retrying.
- Unfulfillable payments: a paid session that deterministically cannot become a contract or a milestone funding is logged as `payment.unfulfillable` (error, with the session, payment intent, reason and offer, job, contract and milestone ids), refunded in full with reason `requested_by_customer` (idempotency key `refund:<pi>:<reason>`) and answered with 200. Permanent reasons: `offer_not_found` (no proposal, job, client or conversation row for the session), `proposal_not_interviewed`, `milestones_invalid` (none, a non-positive or unsafe amount, or an unsafe total), `amount_mismatch` (customer, currency or first milestone amount differs from what was paid) and `milestone_not_fundable` (the funded milestone is missing, not pending or its contract is not active, and no other session funded it). Duplicates keep reason `duplicate` (`refund:<pi>:duplicate`). Anything else, such as a database error or timeout, still throws so Stripe retries, and nothing is refunded. A session that already funds a milestone is never refunded, so replays of a successful webhook are silent. The refund is idempotent at Stripe, so a replay of an unfulfillable webhook repeats the call with the same key and creates no second refund.
- Refund on cancel: declining or withdrawing a `PENDING` contract commits the cancellation and the job release first, then refunds the first milestone payment in full (`requested_by_customer`, key `refund:<pi>:requested_by_customer`) outside the transaction. A failed refund leaves the contract `CANCELLED` and is repaired by repeating the call; see ADR 0007, item c.
- Missing payment intent: when a refund is needed and the session has none, the handler logs `payment.refund.unavailable` (error) and answers 200; retries cannot fix it, so it no longer throws 500. Superseded by "Update 2026-11-19: webhook refund failures" below.
- Not done: no Stripe credit note for the refunded invoice, and no checkout-time milestone snapshot (the contract is still built from the job's milestones at webhook time; the amount check and the job lock bound the exposure). Contracts created before this change leave their job PUBLISHED.
- Update 2026-11-19: the Refunds bullet above names the key `refund:<paymentIntentId>`. The code builds `refund:<paymentIntentId>:<reason>` (`refund:<pi>:duplicate` for duplicates, `refund:<pi>:requested_by_customer` for unfulfillable payments and for decline or withdraw); the key is built in `refundTarget` in `contracts.checkout.service.ts`. Cancel-path refunds now also persist their result on the contract (ADR 0007, update 2026-11-19).
- Client-visible: 409 `JOB_LOCKED` on update and delete of a HIRED job (previously 404), 409 `CONTRACT_EXISTS` and `JOB_ALREADY_HIRED` on `POST /contracts/checkout`. `docs/api/openapi.json` gained these three 409 responses and nothing else.

## Update 2026-11-19: webhook refund failures

Scope: the Stripe contract webhook (`handleContractWebhook`), in the paths that refund without a cancel: a duplicate payment (`refundUnrecordedPayment`, `refundDuplicatePayment`) and an unfulfillable payment (`refundUnfulfillablePayment`), both through `issueRefund` in `contracts.checkout.service.ts`. The cancel path (`refundContractFirstPayment`, ADR 0007 item c) and the reconciler (ADR 0023) keep their behavior and tests. No schema, route or response change; `docs/api/openapi.json` is unchanged.

Answer rules of the webhook when a refund is needed:

| Situation                                                                                                                                    | Answer | Log (level)                                                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------- |
| Refund created, or `charge_already_refunded`                                                                                                 | 200    | `payment.refunded` (warn) when created                                                                         |
| Permanent Stripe code: `charge_not_refundable`, `refund_disputed_payment`, `resource_missing`                                                | 200    | `payment.refund.failed` (error, error name), then `payment.refund.unrecoverable` (error, fields below)         |
| Connection error, rate limit, status 429 or 5xx, any other code, no code, unknown error                                                      | 500    | `payment.refund.failed` (error, error name); Stripe redelivers                                                 |
| Payment intent not on the event: retrieved once from the Checkout Session (`expand: ["payment_intent"]`), found, refunded with the usual key | 200    | none beyond the normal refund logs                                                                             |
| Payment intent still missing after the retrieve                                                                                              | 500    | `payment.refund.no_payment_intent` (error: `stripe.checkout_session_id`, `stripe.event_id`); Stripe redelivers |
| The session retrieve itself fails (connection error, rate limit, 5xx, anything)                                                              | 500    | none of the above; the error middleware logs the 5xx                                                           |

- The permanent codes are the list the reconciler parks on (`REFUND_RECONCILIATION.permanentErrorCodes`). Both callers use one classifier, `isPermanentRefundCode` in `modules/contracts/utils/contracts.stripe-errors.ts`, which also holds `isStripeUnavailable` and `stripeErrorFields` (moved from the reconciler without a change in behavior).
- `payment.refund.unrecoverable` carries only `stripe.event_id`, `stripe.payment_intent_id` and `error.code`: no message, customer or card data. The webhook answers 200 because a redelivery can never fix these codes. The money stays with the platform and needs a manual action in Stripe (for example after a dispute is resolved); there is no stored state to retry from.
- The event id reaches the refund helpers through an `AsyncLocalStorage` set by `handleContractWebhook` (`utils/contracts.webhook-context.ts`), so the service signatures did not change. Outside a webhook the id is logged as null.
- Only the webhook callers resolve a missing payment intent this way, through `resolveContractPaymentIntentId` with `expandPaymentIntent: true`; the cancel path and the reconciler keep calling it without the option and keep `payment.refund.unavailable` (502 on decline or withdraw). The old behavior for a missing intent (log `payment.refund.unavailable`, answer 200) is gone: the money would have stayed with the platform with nothing to retry it.
- Replay and signature behavior are unchanged: a replay of the winning webhook finds the recorded session id and never reaches the refund, and a bad signature is still a 400 before any handler runs.
- Operators should alert on `payment.refund.unrecoverable` and `payment.refund.no_payment_intent`. A `no_payment_intent` 500 that persists until Stripe stops redelivering (up to three days in live mode, per Stripe's webhook documentation; not verified here) leaves a paid session that has no contract or milestone and no refund. That is the orphan case below.

## Orphan paid sessions, follow-up

Status: design only. Not implemented: no code, cron, env variable or log name below exists today. Written from the code and the `stripe` 23.1.0 types (`Checkout.SessionListParams`, `Checkout.Session`).

### How an orphan can arise today

An orphan is a Checkout Session with `payment_status = 'paid'`, no `contract_milestones` row that stores its id in `stripe_checkout_session_id`, and a payment intent that is not fully refunded. Paths in the code:

1. The webhook never reaches a handler: endpoint down or unreachable beyond Stripe's redelivery window, a 400 from signature verification because of a wrong secret, or the event types not enabled on the endpoint (`checkout.session.completed` and `checkout.session.async_payment_succeeded` are the two handled).
2. The handler fails the same way on every delivery until the window ends: the 400 `Stripe contract metadata is missing.`, the 500 `Contract owner could not be resolved.`, a persistent database failure, or, since the update above, a missing payment intent that stays missing.
3. A permanent refund error is acknowledged with 200 (`payment.refund.unrecoverable`). The session has no milestone row and its intent is not refunded, by design.
4. A delayed payment method: the session completes with `payment_status = 'unpaid'` (the handlers return without acting) and becomes `paid` later; if `checkout.session.async_payment_succeeded` is lost, nothing records the payment. Whether such methods are enabled is a Stripe dashboard setting, not visible in the code (`mode: "payment"` with no `payment_method_types`).
5. A crash or transaction failure after the refund call succeeded at Stripe but before the process answered 200 is not an orphan: the redelivery finds the same idempotency key and `charge_already_refunded`.

### How candidates are listed and linked

- `stripe.checkout.sessions.list` takes `created` (a `RangeQueryParam` with `gt`, `gte`, `lt`, `lte`), `status` (`complete`, `expired`, `open`), `limit` (1 to 100), cursors and `expand`. It has no `payment_status` or metadata filter: `status: 'complete'` is applied by Stripe, `payment_status === 'paid'` and the metadata check are applied in code. The list also returns sessions of other flows in the same Stripe account, so the code keeps only `metadata.paymentType` of `CONTRACT_MILESTONE` or `CONTRACT_MILESTONE_FUNDING`.
- Link to our data: both session kinds are created with `client_reference_id` and metadata (`createContractCheckout`: proposal id, metadata `proposalId`, `jobId`, `clientId`; `createMilestoneFundingCheckout`: milestone id, metadata `contractId`, `milestoneId`, `clientId`). The webhook records a session by writing its id to `contract_milestones.stripe_checkout_session_id` (position 0 for a new contract, the funded milestone otherwise), the same lookup `refundUnrecordedPayment` uses. The column is unique, so one batched `WHERE stripe_checkout_session_id = ANY($1)` per list page is an index lookup. The metadata ids are for the log line and for an operator; they are not needed to decide.
- Refund state comes with the list: `expand: ["data.payment_intent.latest_charge"]` gives `latest_charge.amount_refunded` and `payment_intent.amount_received`, the comparison the reconciler already makes (`isPaymentIntentRefunded`), so no per-candidate Stripe call is needed. Sessions the webhook already refunded as duplicate or unfulfillable have no milestone row and a refunded intent, and are not orphans. The expansion depth (three levels under `data`) is within Stripe's documented limit, but it was not run against Stripe in this task.

### False-positive window and minimum age

- A session can be paid until its `expires_at`, which the code sets to 35 minutes after creation. Webhook delivery normally takes seconds, but a delivery that failed once is in Stripe's redelivery schedule, and a session whose handler is retrying looks like an orphan until a retry succeeds.
- Proposal: a minimum age of 2 hours from `created` (35 minutes of payment time plus the first redelivery attempts), and `retries_exhausted = true` in the log when the age is 3 days or more. Only `retries_exhausted = true` should page; the rest is information, because those sessions may still heal on their own.
- A delayed payment method breaks the age bound, because `created` can be days before the payment. Mitigation without a new table: remember session ids in a process-local set and alert only on the second sighting in consecutive runs (it resets on restart, which costs one extra run of delay).

### Cost per run

Assumptions, stated so they can be replaced: 300 completed sessions per day in the Stripe account (about 200 from contracts, the rest from other flows); lookback of 4 days (the three-day redelivery window and a day of margin) up to the minimum age.

- 4 days is about 1,200 completed sessions, 12 list calls of 100 per run, plus 12 indexed database queries and no per-session Stripe call.
- Hourly: about 290 Stripe list calls and 290 queries a day. Stripe's default live read limit is 100 requests a second, so a run of 12 sequential calls is far from it.
- At 10 times the volume (3,000 a day, 120 calls a run) an hourly run is still under the limit but wasteful; run every 6 hours instead (about 480 calls a day).

### Recommended design (detect only)

- Service: `detectOrphanPaidSessions({ now?, minAgeMs?, lookbackMs? })` in `modules/contracts/services/contracts.orphan-sessions.service.ts`, with one batched read function in a repository (`findRecordedCheckoutSessionIds(executor, sessionIds)`, executor first, SQL only; contracts owns `contract_milestones`, so no new table edge). It pages `checkout.sessions.list` with `created: { gte: now - lookback, lte: now - minAge }`, `status: 'complete'`, the expand above and `limit: 100`, filters in code, and logs. It writes nothing, refunds nothing and sends no notification.
- Cadence: hourly (`7 * * * *`, off the 15-minute reconciler ticks), through `contracts.cron.ts` with the same per-process overlap guard, the same catch-all error log and the same shutdown drain as the reconciler. It must not run at boot.
- Mode switch: its own variable, `ORPHAN_PAYMENT_DETECTION_MODE`, `off` or `detect`, default `detect`, validated in `src/config/env.ts` like `REFUND_RECONCILIATION_MODE`. Reusing the reconciler variable is not recommended: that one is a switch for moving money (`on`), and a detector that only reads should stay controllable on its own. There is no `on` value; if automatic refunds of orphans are ever wanted, that is a separate decision with its own rollout.
- Logs: `payment.orphan.detected` (warn) per orphan with `stripe.checkout_session_id`, `stripe.payment_intent_id`, the payment type, `session.age_seconds` and `retries_exhausted`, at most 50 per run; `payment.orphan.run` (info) once per run with the scanned and orphan counts; `payment.orphan.failed` (error, error code only) when a run throws; `payment.orphan.disabled` (info) at startup in mode `off`. No customer or card data. As with `detect` in ADR 0023, the same orphan is logged on every tick; count distinct session ids.
- Without a Stripe key a run logs a skip and touches nothing, as the reconciler does.
- Open questions: whether the Stripe account enables delayed payment methods; whether the production webhook endpoint subscribes to both handled event types; the real daily session volume. These change the cost and the false-positive handling above.

## Consequences

- Frontends must stop sending `imageId` and cover urls that are not already stored for the user. The apps use mock data today, so nothing breaks yet.
- **Heads-up for frontend wiring:** tokens without an `azp` claim now get 401 (Clerk rejects a missing `azp` once `authorizedParties` is set, and the match is exact). This has not been verified with real Clerk tokens. Verify it with real session tokens from each dashboard origin when the apps start calling the API, and confirm that every origin that calls the API is in the dashboard origin list. Non-browser clients must send a token with an `azp` claim.
- Every `isAuthenticated` route requires an existing account for the claimed role.
- Resend cannot run within 60 seconds of creating an invitation, because creating one also sets `updated_at`.
- Not verified without running services: Clerk `azp` behaviour with real tokens, ImageKit behaviour on delete, production boot with the real environment.
