# 0022: Job feeds evaluated in SQL

Status: accepted. Implemented for `filter=recent` and `filter=best-match` on the freelancer and agency job feeds.

## Context

Both job feeds (`GET /freelancer/jobs`, `GET /agency/jobs`) loaded every published job with its client columns, plus a count of every proposal and every hire in the system, then filtered, scored, sorted and sliced in JavaScript. Each request cost three whole-table reads and memory proportional to all jobs, whatever `limit` and `offset` were. `filter=recent` was moved to SQL first; `filter=best-match` still used the old pipeline.

## Decision

1. **Two queries per page.** Q1 returns the ids of the page, with the score for best-match, filtered, ordered and cut by `LIMIT limit + 1 OFFSET offset` in SQL. Q2 (`listFeedJobsByIds`) loads the client columns and the proposal and hire counts for the page ids only, as correlated subqueries. `hasMore` comes from `toOffsetPage` over the `limit + 1` ids. An empty page skips Q2. The service puts the Q2 rows back in Q1 order.
2. **Shared filters.** `filter=recent` (`listRecentJobIds`) and `filter=best-match` (`listBestMatchJobIds`) build their predicates with the same `feedConditions` function (status, levels, durations, budget range, proposal count range, payment verified, same inner joins). Indexes already exist (`job_posts_published_feed_idx`); no schema or migration change.
3. **Score, integers only.** `score = 2 * skill_hits + content_hits`. `skill_hits` is the number of caller skills for which some job skill contains the caller skill after normalization; `content_hits` is the number of caller skills contained in the normalized `title || ' ' || description`. Rows with `score > 0` are kept before ordering and paging. `matchScore` in the response comes from Q1 and is present for best-match only; the response schemas and `docs/api/openapi.json` are unchanged.
4. **Normalization has one definition per side.** The caller skills are normalized in JavaScript (`normalizeSkill`: lowercase, strip everything except `a-z0-9`) and passed as a `text[]`. The job side uses `regexp_replace(lower(x), '[^a-z0-9]', '', 'g')`. The caller skills are neither deduplicated nor stripped of empty entries.
5. **Ordering.** `score DESC`, then `date_trunc('milliseconds', coalesce(published_at, created_at, 'epoch'))` `DESC`, then `id DESC`. JavaScript dates have millisecond precision and the reference sort compared them; truncating the timestamp in SQL keeps the order identical, and the `id` tie-break makes it total.
6. **Preserved behaviour.** A caller skill that normalizes to the empty string matches every job (content always; skill only when the job has at least one skill). A duplicated caller skill counts each time. An empty skill list answers an empty feed without a query. Jobs the caller already applied to are not hidden. NULL `published_at` and `created_at` fall back as above. NULL elements in a job's `skills` array are skipped in SQL; the API cannot produce them.
7. **Parity test as the acceptance test.** `freelancer.job-feed.parity.test.ts` keeps a self-contained copy of the old pipeline (the reference) and compares it with the production entry points over a matrix of callers, filters and pages. The reference lives only in that test. The production functions `listPublishedJobsWithClient`, `countProposalsPerJob`, `countHiresPerJob` and the JavaScript scoring, sorting and slicing are removed.

## Consequences

- Best-match is still O(published jobs) CPU per request: the content match is a substring test on normalized text and cannot use an index, so every filtered published job is scored. Measured on the test database, inside a rolled-back transaction, with 20,000 published jobs, 100,000 proposals and a 3-skill caller: Q1 executes in about 0.60 s at offset 0 (597 ms) and about 0.60 s at offset 5000 (604 ms), with a sequential scan of `job_posts`, about 1,450 shared buffer hits and a top-N sort; the cost is about 30 microseconds per job and does not depend on the offset. Extrapolated linearly, about 3 s at 100,000 published jobs, which is too slow for a request path; at a few thousand jobs it is tens of milliseconds. The page rows (Q2) are bounded by `limit` and cost the same as for `filter=recent`.
- Memory per request is now bounded by the page, not by the number of jobs, and the three whole-table reads are gone: a freelancer request ran the profile lookup plus 3 queries returning every published job and every proposal and hire group; it now runs the profile lookup plus 2 queries returning at most `limit + 1` ids and `limit` rows (1 query when the page is empty).
- If best-match becomes a bottleneck, store a normalized search column (`job_posts.search_text` and a normalized skills array) written in the jobs write path as in ADR 0019, optionally with a `pg_trgm` GIN index, so the match can use an index or at least skip the per-row normalization.
- A deep offset still scores and sorts every matching row (top-N sort of `offset + limit + 1` entries); `offset` is capped at 10,000 by the pagination schema.
- The job-side normalization in SQL and the caller-side normalization in JavaScript must stay equal; the parity test and the repository tests pin both.
