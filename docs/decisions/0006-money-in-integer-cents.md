# 0006: Money in integer cents

Status: accepted (Stage 5b). Supersedes the "Amounts" parts of ADR 0005.

## Context

Money was `numeric(p,2)` in Postgres and a JavaScript float in code. Fees used `Math.round(gross * 0.1 * 100) / 100`, which rounds exact half-cent ties down. Over gross values of 1 to 20,000,000 cents, 52,428 (0.26%) differ from half-up rounding, for example 35 cents gives a fee of 3 instead of 4. Dollar values were also stored in JSON (`job_posts.milestones[].budget`, `messages.event_payload.amount`, `notifications.metadata.amount`) and in RabbitMQ notification events.

## Decision

- Every money value is an integer number of cents (USD). DB columns are `bigint` read as a JS number (`mode: "number"`). Each column has a `<table>_<column>_max_check` CHECK, `<= 9007199254740991`, so values stay safe integers in JS.
- Column rename: every money column ends in `_cents`. `earning_history.platform_fee_amount` is now `platform_fee_cents`. `connects_purchase_history.amount_paid` is now `amount_paid_cents`. `connects_history.amount` is a connects count and is unchanged.
- Fee rounding is fixed: half-up on cents, `fee = floor((gross * 1000 + 5000) / 10000)`, `net = gross - fee`, in `utils/money.ts` `splitFee` (BigInt arithmetic). The fee rate is `PLATFORM_FEE_BPS = 1000`. The fee model itself (rate, hold, who pays) is still "to confirm" in `docs/product.md`; only the rounding rule is decided.
- `splitFee` throws when the net would be below 1 cent. `earning_history` has `CHECK (platform_fee_cents >= 0)` and `CHECK (platform_fee_cents < amount_cents)`. The payout code no longer has a non-positive-net path (`reportNonPositiveNet` and the old non-retryable `invalid_amount` branch are removed). A guard `amount_cents >= 1` stays right before `transfers.create` as defense in depth.
- API: every money field, response, request body and query filter ends in `Cents`, keeping the endpoint's existing casing (`totalBudgetCents`, `minBudgetCents`, `hourly_rate_cents`). Requests carry integers and are validated with zod at the route boundary. Stripe amounts are used as they are.
- JSON: `budget` becomes `budgetCents`, `amount` becomes `amountCents`, `firstMilestone.amount` becomes `firstMilestone.amountCents`.
- Payout recovery (`transfers.list` adoption) compares `transfer.amount` with `payout_history.amount_cents` directly.

## Migration `0002_money_to_cents`

- Hand-written, one transaction. It fails loudly and never skips: a missing, non-numeric, negative, over-2-decimal or above-safe-integer money value in any JSON location aborts the whole migration, as does an `amount` or `budget` key left on an event type it does not handle (the final guard is a structured `jsonb_path_exists(col, '$.**.<key>')` over keys, so free text cannot trip it).
- Contracts whose `total_amount` differs from the sum of their milestones are not changed. They are reported by the preflight query so a person decides.
- Verified in a scratch database with seeded rows for every JSON event type, job milestones, notifications, `amount_paid`, contracts, earnings and payouts. 14 abort cases (3 decimals in each location, missing keys, string and negative values, above the safe limit, an unhandled type with an amount key, a late CHECK failure) all exit non-zero and leave the schema and data byte-identical.
- Stored fees are converted as they are, not recomputed. Rows that differ from half-up are only reported.

## RabbitMQ

The notification envelope is version 2 and carries `metadata.amountCents`. The publisher always emits version 2. The consumer still accepts version 1 and converts `metadata.amount` (dollars) to `amountCents` in one helper, `src/events/legacy-v1.ts`, which rejects values with more than 2 decimals to the DLQ.

Remove version 1 support (the helper, the v1 schema branch and its tests) once no version 1 message can exist: every environment runs a version 2 publisher, and the main queue and the DLQ have been drained or purged after that deploy. Replaying an old DLQ message before then is safe because of the helper.

## Known debt (limits kept exactly, not fixed here)

- Freelancer hourly rate: zod allows 5.00 to 1,000.00 but the old column held up to 9,999.99.
- Bid amount and job total budget: zod allows up to 1,000,000.00 but the old columns held up to 9,999,999.99.
- `connects_purchase_history.amount_paid` had no precision or limit.
- Minimums disagree: a job milestone must be above $5.00 (501 cents), a job total at least $5.00, and a contract milestone at least $10.00.
- Contract milestone amounts have no upper zod limit other than the safe integer; job milestones are capped at 1,000,000.00.
- `POST /contracts/:contractId/milestones` validates `amountCents` inside the controller (`createAdditionalMilestone`) instead of a zod schema at the route. The limit is unchanged (at least 1000 cents). It should move to a `contracts.schemas.ts` body schema.
- `contracts.total_amount_cents` is not enforced to equal the sum of its milestones.
- PG 18 keeps the old auto-generated NOT NULL constraint names on renamed columns (for example `agency_earning_total_earning_not_null`). This is cosmetic.
- The dashboards use mock data and do not call the API yet, so none of the renamed fields are consumed.
- Log attributes were renamed (`payment.amount` is now `payment.amount_cents`).

## Contract changes for the frontend

All amounts are integer cents. Each renamed field below only gains the `Cents` suffix (old name, new name). Requests with fractional, negative, string or too-large values get a 400. Query filters must be digits only; a bad filter is now a 400 instead of being ignored. `feeRatePercent` stays a percent (`PLATFORM_FEE_BPS / 100`).
