# 0029: Notification outbox and in-process relay

Status: accepted (2026-11-27, learning roadmap item 1.4). Label: adopted for learning. Part A: table, module, relay, flag and wiring. Part B (2026-11-27): the 8 direct-publish call sites use the outbox; see "Part B: call sites" below.

## Context

ADR 0024 writes the must-not-lose notices as rows inside the business transaction. Eight notices still go straight to RabbitMQ through `sendNotification` after commit: CONTRACT_ACCEPTED, MILESTONE_ADDED, CONTRACT_COMPLETED, REVIEW_RECEIVED, PROPOSAL_RECEIVED, PROPOSAL_VIEWED, the answered-invitation notice and AGENCY_WELCOME_BONUS. A broker outage or a crash between commit and publish loses them; the only signal is `queue.publish.skipped` or `queue.publish.failed`.

These eight are best-effort by product choice. No loss has been observed, and the trigger in `docs/research/backend-evolution/03-roadmap.md` (loss observed) has not fired, so the outbox is not needed. It is built to learn the transactional outbox pattern (`docs/research/backend-evolution/04-learning-roadmap.md`, Part 3, 1.4) behind a flag that defaults to `off`.

## Options

| Option                                         | For                                                                                                                          | Against                                                                                                                                                                                            |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| In-process poll (chosen)                       | One loop in the API process; reuses the ADR 0023 claim shape; works on any Postgres; easy to stop and drain in `shutdown.ts` | Up to about 1 s of extra latency in `on`; one small query per second while idle                                                                                                                    |
| `LISTEN/NOTIFY` wake-up                        | Lower latency                                                                                                                | Needs a dedicated long-lived connection outside the pool; a notification is lost while that connection is down, so a poll is still needed as a fallback; more moving parts for no correctness gain |
| CDC (logical replication, Debezium or similar) | No polling; no relay code in the API                                                                                         | Needs a replication slot, another service and its operations; managed Postgres plans differ; far more than a single-instance project needs                                                         |

## Decision

1. Table `outbox_events` (migration `0011_outbox_events`, owner module `outbox`): `id`, `event_id` (unique, the envelope id), `payload` (a `NotificationInput` without `eventId`; money only as cents, the envelope `metadata` rules apply), `traceparent`, `status` (`PENDING`, `PUBLISHING`, `PUBLISHED`, `DEAD`, check constraint), `attempts`, `next_attempt_at`, `claimed_at`, `last_error` (a short code, at most 500 characters), `created_at`, `published_at`. Partial index `outbox_events_due_idx (next_attempt_at) WHERE status IN ('PENDING','PUBLISHING')`, index `outbox_events_status_published_idx (status, published_at)` for retention.
2. Module `outbox` at layer 0 (`import-boundaries.test.ts`, `table-ownership.ts`). Its `index.ts` exports `enqueueNotification(executor, input & { eventId })`, `sendUnlessQueued(queued, input)`, `startOutboxRelay`, `stopOutboxRelay`, `waitForOutboxRelayRun` and `getOutboxStats`. The relay lives in the module, not in `infrastructure/events`, because SQL is allowed only in repositories (`repository-sql.test.ts`) and infrastructure may not import modules (`import-boundaries.test.ts`). The module imports `sendNotification`, `isRabbitEnabled` and `isRabbitConnected` from infrastructure.
3. Flag `OUTBOX_MODE` (`off` default, `shadow`, `on`; `config/env.ts`). `off`: `enqueueNotification` inserts nothing and returns `false`; callers send directly. `shadow`: the row is inserted in the caller's transaction and the function returns `false`, so the caller still sends directly after commit; the relay publishes too and the consumer's unique `event_id` (`insertNotificationIfNew`) absorbs the duplicate. `on`: the row is inserted and the function returns `true`; there is no direct send. Every mode counts as `off` when `isRabbitEnabled()` is false, so rows never pile up without a broker. `eventId` is mandatory, built with `notificationEventId`.
4. Relay (`outbox.cron.ts`): a self-rescheduling, `unref`'d `setTimeout` loop, not `node-cron`. It waits 1 s when idle and re-runs at once after a full batch. It claims nothing while the broker is disconnected (`isRabbitConnected()`), so an outage does not burn attempts. Claim, after ADR 0023: `WITH picked AS MATERIALIZED (SELECT id ... WHERE (status='PENDING' AND next_attempt_at <= now()) OR (status='PUBLISHING' AND claimed_at < now() - lease) ORDER BY next_attempt_at, id LIMIT 50 FOR UPDATE SKIP LOCKED) UPDATE ... SET status='PUBLISHING', claimed_at=now(), attempts=attempts+1 FROM picked`. Lease 60 s. Each claimed row is validated against the envelope payload schema (an invalid payload goes to `DEAD`, `invalid_payload`) and sent with `sendNotification({ ...payload, eventId })`. Every result is written by one guarded `UPDATE ... WHERE id=$ AND status='PUBLISHING' AND attempts=$claimed`. `published` sets `PUBLISHED`. `failed` sets `PENDING` with `next_attempt_at = now() + min(5 s * 2^(attempts-1), 10 min)`, or `DEAD` once `attempts >= 10`. `disabled` releases the row (`attempts - 1`) and warns once (`outbox.relay.disabled`). A guarded update that matches nothing logs `outbox.relay.lease_lost` (warn): the lease expired and another tick owns the row. Rows are sent one at a time. Before each send the relay checks the broker connection and a 30 s batch budget (half the lease); when either fails, the unsent rows are released (`attempts - 1`, due now). The first `failed` publish ends the batch the same way, so a blocked or flapping broker costs one attempt per tick, not one per row. A row reclaimed after its lease with `attempts` above 10 goes to `DEAD` (`lease_expired_after_max_attempts`) without a send, so a row that crashes the process on every send cannot loop forever. A database error during a row is logged as `outbox.relay.failed` and ends the batch; the remaining rows wait for their lease.
5. Publisher confirm: `sendNotification` returns `"published"` only after the broker confirm. The publish channel is created with `confirm: true`, and in amqp-connection-manager 5.0.1 `ChannelWrapper.publish` resolves only inside the amqplib confirm callback without error. A nack or the 2 s `PUBLISH_TIMEOUT_MS` rejects, and `sendNotification` returns `"failed"`. A timed-out message may still reach the broker, so a retry can publish a duplicate; the consumer dedupes it on `event_id`.
6. Retention and signals: published rows older than 7 days are deleted in batches of 500 (materialized id subquery) at most once a minute from the relay tick. Stats are read at most every 10 s. Logs: `outbox.relay.failed` (error, a tick threw), `outbox.relay.lag` (warn, oldest pending row older than 60 s, at most once a minute), `outbox.event.dead` (error, alert on it); all three are in `COUNTED_LOG_EVENTS`. Gauges `outbox.pending`, `outbox.oldest_pending_age_ms` and `outbox.dead` are registered through `registerOutboxGauges` (`infrastructure/telemetry/gauges.ts`) only when telemetry is on and the relay runs.
7. Trace link: when `TELEMETRY_MODE` is not `off`, `enqueueNotification` stores the active span as a W3C `traceparent`, and the relay runs each send in a `outbox.relay.publish` span (kind producer) with a link to it. With telemetry off nothing is read and no span is started.
8. Wiring: `bootstrap/start.ts` starts the relay after the notification consumer and the dead-letter monitor, only when RabbitMQ is enabled and the mode is not `off`. `shutdown.ts` stops the relay before the drain step, awaits its in-flight tick inside the drain step (bounded by `PAYOUT_DRAIN_TIMEOUT_MS`, `system.shutdown.outbox_relay_run_timeout`), and only later closes RabbitMQ and the pool. A startup failure also stops the relay and awaits its tick before the consumer and RabbitMQ close.

## Consequences

- Delivery in `on` is at-least-once from the outbox to the broker and exactly-once into `notifications`, through the unique `event_id`. A crash between publish and the `PUBLISHED` mark republishes after the lease; `outbox.relay.integration.test.ts` relays one row twice through a real broker and finds one `notifications` row.
- RabbitMQ down for hours in `on`: the relay claims nothing, rows stay `PENDING` and the table grows by one row per notice. `outbox.relay.lag` fires once a minute, and `outbox.pending` and `outbox.oldest_pending_age_ms` show the backlog. Rows drain at up to 50 per tick, back to back, once the broker returns. Attempts are spent only on real publish failures while connected, at most one row per tick, so a row reaches `DEAD` only after 10 such failures of its own (about 30 minutes of backoff).
- Tests: `outbox.repository.integration.test.ts` (idempotent insert, rollback leaves no row, a claim skips rows another transaction holds without blocking, two concurrent claims are disjoint, lease reclaim, stale guarded marks change nothing, retention, stats), `outbox.service.test.ts`, `outbox.trace.test.ts`, the bootstrap wiring tests, and the broker test. Both integration files are in the serial `payout-totals` vitest project because claims and retention act on the whole table. Mutation checks: without `SKIP LOCKED` the skip test fails; without the `attempts` guard the stale-mark test fails.
- Closed in part B: `enqueueNotification` validates the payload with the envelope payload schema (the one the relay uses) in `shadow` and `on` and throws `OutboxPayloadError`, so a malformed notice fails its business transaction instead of committing and going `DEAD`. In `off` it validates nothing, so `off` behaves as before. Closed in part B: `startOutboxRelay` does not schedule a tick while one is in flight; the in-flight tick reschedules itself, so a stop and start during a tick keeps one loop (`outbox.cron.test.ts`).
- Still open: the claim's OR predicate scans the whole partial index when fewer than 50 rows are due, which costs time only with a large backoff backlog. The small fix (set `next_attempt_at = now() + lease` on claim and drop the `claimed_at` branch, so one range condition serves both statuses) changes the lease semantics and the setup of the existing lease test, and rows claimed by the previous code would be reclaimed at once after deploy. It is left for a later change with its own test; a backlog large enough to matter would show first in `outbox.oldest_pending_age_ms`.
- No route, schema or response changed; `docs/api/openapi.json` is unchanged.

## Part B: call sites (2026-11-27)

Every site builds its notice once, with a deterministic `notificationEventId`, and passes the same input (with `eventId`) to the outbox and to the direct send, so the consumer's unique `event_id` absorbs the shadow duplicate. The id is now also sent in `off`; that is the only difference from before in `off` (the envelope id is deterministic instead of random). No response, status code or schema changed.

| Kind                                   | Function                                                    | Event id (kind, entity, transition)                        | Business transaction | Rule                                                                                                             |
| -------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| CONTRACT_ACCEPTED (client and talent)  | `acceptContract`, sent by `acceptOffer`                     | contract id, `accepted-client` / `accepted-talent`         | yes                  | enqueued last in the transaction; a failed enqueue rolls the acceptance back                                     |
| CONTRACT_COMPLETED or REVIEW_RECEIVED  | `finishContractWithReview`, sent by `finishContractAsParty` | contract id, `completed` / `review-<client or freelancer>` | yes                  | enqueued last in the transaction (both branches); a failed enqueue rolls the review back                         |
| MILESTONE_ADDED                        | `addContractMilestone`                                      | milestone id, `added`                                      | yes                  | enqueued last in the transaction; a failed enqueue rolls the milestone back                                      |
| PROPOSAL_RECEIVED (freelancer, agency) | `submitProposal`, `submitAgencyProposal`                    | proposal id, `received`                                    | yes                  | enqueued last in the transaction, before the connects cache write; failure rolls back the proposal and the debit |
| PROPOSAL_VIEWED                        | `markProposalViewed`                                        | proposal id, `viewed`                                      | no                   | `enqueueNotificationAfterCommit` after the guarded update; failure logs and sends directly                       |
| AGENCY_INVITATION_ACCEPTED / DECLINED  | `respondToAgencyInvitation`                                 | invitation id, `accepted` / `declined`                     | accept only          | after the write (text needs `syncAccountDisplay`, a Clerk call); failure logs and sends directly                 |
| AGENCY_WELCOME_BONUS                   | `updateAgencyProfile` after `addAgencyConnects`             | agency id, `welcome-bonus`                                 | in `connects`        | after the grant's transaction; failure logs and sends directly                                                   |

- Transaction sites: `const queued = await enqueueNotification(tx, input)` as the last statement inside the transaction, `await sendUnlessQueued(queued, input)` after commit, at the place the old `sendNotification` stood. No money write, connects debit, Stripe call, lock or guarded update moved.
- Sites without a business transaction today are not widened: the brief proposed a short transaction around the guarded `VIEWED` update, but the part B instruction was not to open or widen one, so `enqueueNotificationAfterCommit(input)` writes the row in its own statement after the business write. It never throws: on failure it logs `outbox.enqueue.failed` (warn, counted) and returns `false`, so the caller sends directly as before. A crash between the business write and that statement loses the notice, as before.
- Transitions happen once: acceptance, completion and the `SUBMITTED` to `VIEWED` update are guarded, a review is unique per contract and reviewer (an agency counts as one reviewer), the welcome grant is insert-if-absent, and an invitation is resolved once. A repeat proposal view already sent nothing; it still sends nothing.
- Shadow: the brief and part A define `shadow` as "row in the transaction, direct send, and the relay publishes too"; the consumer stores each `event_id` once. That is kept; the relay is not disabled in `shadow`.
- What a crash costs, per mode: `off` and `shadow` lose a transaction site's direct send if the process dies between commit and publish (in `shadow` the relay still delivers the row). `on` loses nothing after commit: the row is relayed once the process and the broker are back. Post-commit sites lose the notice if the process dies between the business write and the enqueue, in every mode.
- Tests: `contracts.outbox.integration.test.ts`, `proposals.outbox.integration.test.ts`, `agency.outbox.integration.test.ts` (every site in `off`, `shadow` and `on`; for each transaction site a failure injected after the row is written rolls back the business change and leaves no row, and a commit leaves exactly one row per notice; post-commit sites fall back to a direct send), `contracts.outbox-broker.integration.test.ts` (serial project: CONTRACT_ACCEPTED in `on` through the relay and a real broker, relayed twice, stored once per recipient), `outbox.service.test.ts` (validation, post-commit enqueue), `outbox.cron.test.ts` (restart guard). Mutation checks: the acceptance enqueue moved after commit fails the rollback tests; a direct send in `on` in `submitProposal` fails its no-double-publish test; without the restart guard the single-loop test fails.

## Rollout

Per D-4 of the roadmap: `OUTBOX_MODE=shadow` for one week, then `on`. Operator checklist: `docs/test-plans/api-outbox.md`. In shadow, every notice of the eight kinds reaches the broker twice and is stored once; `outbox.pending` should return to 0 within seconds and `outbox.dead` stay 0. Move to `on` only after a week with `outbox.event.dead`, `outbox.relay.failed` and `outbox.enqueue.failed` silent.

## Removal signal

The label is "adopted for learning". Remove the outbox (new ADR superseding this one, flag `off` for a week, one commit removes code and tests, a new migration drops the table) when any of these holds: `outbox.pending` never rises above 0 for 60 days of real use, because the broker never failed (the relay queue is always empty); p95 of the eight request paths regresses by more than 10% against the load baseline because of the extra insert; the relay or its tests cause two flaky runs or an incident; or the learning goal is met and nobody wants to keep the flag. Keep it if a broker outage ever leaves rows that the relay later delivers.

## Rollback

Set `OUTBOX_MODE=shadow` or `off` only after `outbox.pending` is 0; otherwise the remaining rows wait until a relay runs again. Reverting the code leaves the table; a later migration drops it (never edit `0011_outbox_events`).
