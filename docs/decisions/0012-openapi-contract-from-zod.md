# 0012: OpenAPI 3.1 contract generated from route zod schemas

Status: accepted (Stage 9b).

## Context

ADR 0011 attached request schemas to every route and left room for OpenAPI generation. No app calls the API yet, so the frontends need a written contract before wiring. The contract must come from the same zod schemas the server enforces, so it cannot drift from the code.

Mechanism:

- `validate({ params, query, body, responses })` stores `responses` (a status code to zod schema map) next to the request schemas under `VALIDATION_SCHEMAS`. `getValidationSchemas` returns it.
- `src/utils/response-schemas.ts` holds shared schemas: `ok`, `okNoData`, `isoDateTime`, `cents`, `offsetPage`, `cursorPage`, `ErrorBody`, `ValidationErrorBody`, `BadRequestBody` (union of the two), `InternalErrorBody`, `RateLimitBody`.
- Each module has `src/modules/<name>/<name>.responses.ts`. Component ids are prefixed by module so two modules cannot register different definitions under one id (the generator throws on a clash).
- The registry test (`src/routes/route-validation-check.test.ts`) fails when a route has no 2xx entry in `responses`, unless it is allowlisted.
- `src/routes/contract-allowlist.ts` has three lists, each entry with `method`, `path` and a required `reason`: `rawBodyWebhooks` (4: connects, contracts, identity, meetings), `eventStreams` (2: `GET /notifications/stream`, `GET /admin/logs/stream`) and `untestedRoutes` (empty). A route in `untestedRoutes` still declares `responses` and is only skipped by the contract test.
- Generator: `src/openapi/{build-spec,convert-schema,schema-walk,document,generate}.ts`. `build-spec.ts` walks the registered routes and builds the document; `convert-schema.ts` wraps `z.toJSONSchema`; `schema-walk.ts` has the JSON helpers, key sorting, the formatter and the empty-schema check; `document.ts` resolves the output path and mount paths; `generate.ts` is the script.

Generation rules:

- `operationId` is `<module>_<method>_<path words>`, in snake case. A path parameter becomes `by_<name>`. Routes outside a module (`/health`, `/ready`) use the module `system`; `/conversations` belongs to `messaging`. Duplicates throw.
- One tag per module (title-cased).
- Security comes from the middleware on the route: `isAuthenticated`, `identifyAccount` or `verifyBearerToken` gives `clerkBearer`; the admin session middlewares give `adminSession`; no guard gives `[]`. A route with both kinds throws. Routes that check the token inside the controller are listed in `CONTROLLER_AUTH_OVERRIDES` (`src/openapi/build-spec.ts`, each with a reason); today only `POST /auth/sign-up`. A test fails when an entry matches no route.
- On `clerkBearer` operations whose query schema includes `role`, the `role` parameter is marked required (the guards answer 400 "A valid account role is required." without it).
- 400 (validation, when the route has params, query or body), 401 (when secured), 429 and 500 are added centrally from the shared components. A response the route declares itself wins (`??=`).
- Special cases: the PDF certificate (`format: binary` output) is emitted as `application/pdf` with a binary string. The four webhooks are emitted with signature headers, a raw JSON object body, 200 and 400 only. The two event streams get a 200 `text/event-stream`.
- Request-side conversion uses `io: "input"`: preprocess pipes such as the agency `optionalBody` use the inner schema and the body is not required when `undefined` parses. Keys ignored through `withIgnoredKeys` are emitted as optional untyped properties with the description "Accepted for compatibility and ignored by the server." Digit-string query pipes (`pagingDigits` and similar) are emitted as integers. A `{}` schema anywhere in the document is rejected by the generator. Responses use `io: "output"`.

## Decision

### Generator

Use native `z.toJSONSchema` (zod 4.6.7, `draft-2020-12`, which is the OpenAPI 3.1 dialect) with a small wrapper. No new dependency.

Considered: `@asteasolutions/zod-to-openapi` (v8.5.0) and `zod-openapi` (v5.4.2), as listed by context7. They add route registration APIs and their own metadata layer, which duplicates what `validate` already stores. The native output is enough because the wrapper only rewrites `$defs` references to `#/components/schemas/` and applies the rules above.

Revisit when the spec needs features the wrapper does not cover (for example webhooks as OpenAPI `webhooks`, examples per operation) or when the wrapper grows past a few hundred lines.

Risk: zod is `^4.6.7` in `services/api/package.json`, outside the pnpm catalog. A minor bump may change the JSON Schema output bytes. The spec test (`src/openapi/openapi-spec.test.ts`) and the CI drift check catch it; regenerate and review the diff.

### Committed spec

- `docs/api/openapi.json` is committed and generated by `pnpm --filter @onemarketplace/api openapi:generate` (`tsx src/openapi/generate.ts`).
- No runtime endpoint serves it.
- Output is LF, keys are sorted, and the file is stable under Prettier because the generator formats it itself. Two runs give identical bytes.
- The script clears the optional variables, sets `NODE_ENV=development` and dummy `DATABASE_URL` and `REDIS_URL` at runtime, reads no `.env` and connects to nothing.
- It works only from source through `tsx`: `document.ts` reads `src/routes/index.ts` as text to find the router mount paths.
- CI: the `api-test` job in `.github/workflows/ci.yml` runs two added steps after the test run:

```yaml
- name: Regenerate OpenAPI spec
  run: pnpm --filter @onemarketplace/api openapi:generate

- name: Fail if the OpenAPI spec is stale
  run: git diff --exit-code -- docs/api/openapi.json
```

### Responses are documented as they are

Success and error shapes are described as the code returns them, including the inconsistencies listed below. One deliberate exception to "no response-shape changes" was made: the no-agency fallbacks of `GET /agency/earnings/summary` and `GET /agency/earnings/overview` now use the `*Cents` names like the normal shapes.

| Route                           | Before                                          | After                                                                                                           |
| ------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `GET /agency/earnings/summary`  | `currentMonthTotal`, `previousMonthTotal`       | `currentMonthTotalCents`, `previousMonthTotalCents`                                                             |
| `GET /agency/earnings/overview` | `available`, `pending`, `lifetime`, `totalFees` | `availableCents`, `pendingCents`, `withdrawnCents`, `lifetimeCents`, `totalFeesCents` (`withdrawnCents` is new) |

9a leftovers done in this stage, with behavior differences:

- An invalid `sort`, `filter`, `type` or `memberRole` is now a 400 `VALIDATION_ERROR` (it was accepted and fell back to the default).
- Agency `POST /` strips `id`, `imageId`, `createdAt` and `updatedAt` instead of rejecting them (as PUT already did).
- A non-object body on agency `POST /` now gets the zod default message.
- Three unused limits were removed from `validation-limits.ts`.

## Backlog (not fixed in this stage)

- Agency connects checkout bills the requester's Stripe customer instead of the owner's. Product decision for the Stripe verification stage.
- Admin login returns no session token. Check how the admin app authenticates before wiring.
- `hasMore` off-by-one: `rows.length === limit` is a false positive on an exactly full last page. Fix with the `limit + 1` pattern; messaging already does it.
- The freelancer Connects checkout `success_url` has the typo `payment=succes` (`connects.service.ts:254`); the agency one is spelled correctly.
- `BadRequestBody` is a union that is functionally `ErrorBody`.
- On Windows the PDF certificate render prints "fetch failed" on stderr in tests (font fetch).

## Unverified response schemas

A schema is verified when a `*.contract.test.ts` parses a real response with it. Every 2xx (success) schema is verified by a contract test, as is `/health` and `/ready` 200. Declared schemas that no test parses, derived by matching each `<responses object>[status]` in the responses files against the contract tests:

- admin: `redisKeys` 400, login 503.
- agency: create 400, update 400, connects checkout 400, submit proposal 400, payout link 404, invite 400, resend invitation 403.
- auth: sign-up 400.
- client: profile PUT 400 and 404; hiring overview, completed contracts, dashboard overview and marketplace search 403; finance link 403 and 404.
- contracts: submit 400, checkout 400.
- freelancer: profile PUT 400 and 404; earnings summary, earnings overview, earnings certificate, job feed and job detail 403; payout link 404.
- jobs: create 400, update 400; list, save, unsave, get, update and delete 403.
- messaging: open 400, send 400, send 423, messages 400, read 400.
- proposals: list 403, create 400.
- system: `/ready` 503.
- connects, identity, meetings, notifications: none.
- Exempt (no schema): the four webhooks and the two event streams.
- Central components 400 (`ValidationErrorBody`), 401 (`ErrorBody`), 429 (`RateLimitBody`) and 500 (`InternalErrorBody`) are not parsed against a real response by any contract test. `src/utils/response-schemas.test.ts` covers them only with hand-written samples.

## Review follow-ups

1. `POST /auth/sign-up` is documented with `clerkBearer` through `CONTROLLER_AUTH_OVERRIDES`; the controller authenticates the token itself. No other HTTP controller does (the messaging socket uses `authenticateAccount` outside HTTP).
2. Admin login declares 401 (wrong password) and 503 (admin auth not configured); the `adminSession` scheme describes the token format instead of claiming login returns it.
3. `role` is required on Clerk-secured operations that declare it, and the cross-cutting 400 is noted above.
4. Contract tests for contracts client and freelancer lists assert the expected length instead of only parsing.

The open items of ADR 0011 were marked Done; this ADR is where they are tracked now.

## Consequences

- The contract is generated from the code, so drift is a CI failure, not a review item.
- The spec documents the current inconsistencies; fixing them later changes the committed spec in the same diff.
- Adding a route:
  1. Declare `params`, `query`, `body` and `responses` (with a 2xx entry) in `validate`, with the schemas in `<name>.schemas.ts` and `<name>.responses.ts`.
  2. Add a contract test that parses real responses with those schemas. Allowlist only raw-body webhooks and event streams, with a reason, in `src/routes/contract-allowlist.ts`.
  3. Run `pnpm --filter @onemarketplace/api openapi:generate`.
  4. Commit the regenerated `docs/api/openapi.json`.
- Typed-client generation from the spec is out of scope for now.
