# 0007: Guarded state transitions

Status: accepted (Stage 5d). Extends the Stage 5c pattern (meeting end, milestone review). Does not change ADR 0005.

File paths in this ADR predate the module refactor; current locations are in docs/architecture.md.

## Context

Several status changes in `contracts.service.ts` and `meetings.service.ts` read a row, decided in JavaScript, then updated by id only. Two requests could both pass the read and both write: a second submit or finish worked on a stale state, a milestone could be added to a contract that was finishing, and two `startMeeting` calls could create two ACTIVE meetings. Races surfaced as 500s or as corrupted state.

## Decision

- Every status transition is one guarded conditional `UPDATE ... WHERE status = <expected> ... RETURNING`. Zero rows means a lost race or an invalid state, and the service answers 409 with a code.
- A change that touches several tables runs in one transaction. Notifications, socket/SSE emits, Stripe calls and queue publishes happen only after commit.
- The Stage 5c inline pattern is reused in each service. There is no shared helper. `payout-state.ts` stays payouts-only (ADR 0005).
- `ApiError` gained an optional `code`. `error.middleware.ts` serializes it as `code` in 4xx bodies only when set (5xx bodies never carry it). Only the 409s of the transitions below (submit, accept, add, finish), including their sequential pre-checks, set a code; unrelated errors are not retrofitted.

### Why add and finish take a lock

A `NOT EXISTS` subquery inside the `UPDATE` does not see rows committed after the statement's snapshot, so a finish could complete a contract while a concurrent add commits a new incomplete milestone. Both operations therefore lock the contract row `FOR UPDATE` first and check the milestone state in a separate statement, which takes a fresh snapshot after the lock is granted. The test "serializes an add behind a finish that already read its milestone check" and mutation checks 5 and 6 cover this.

### Submit

Resubmitting an `ACTIVE`, funded milestone stays allowed (changes requested, then work sent again). A concurrent double submit therefore equals two sequential resubmits and is not an error.

### startMeeting

- Invariant: at most one ACTIVE meeting per `conversation_id`. It is derived from the early return in `startMeeting` for an existing ACTIVE meeting.
- It is enforced by the partial unique index `meetings_one_active_per_conversation_unique` (`drizzle/0003_brave_legion.sql`, `WHERE status = 'ACTIVE'`). The migration does not fix data. The maintainer reports that existing dev data was checked and has 0 violations.
- One transaction: meeting insert, `MEETING_STARTED` system message through `postSystemEventMessage` with `{ executor: transaction }`, then `message_id`. The emit runs after commit; its failure is logged (`task.meeting.emit_failed`) and does not fail the start.
- On `23505` for that index, the existing ACTIVE meeting is returned. The Daily room created by the loser is not deleted; it is logged as `task.meeting.room_orphaned` with the room name.

## Client-visible changes

| Case                                                                                | Before                          | Now                                      |
| ----------------------------------------------------------------------------------- | ------------------------------- | ---------------------------------------- |
| Submit on a milestone that is not ACTIVE and funded (including races)               | Update by id, no check          | 409 `MILESTONE_NOT_SUBMITTABLE`          |
| Accept offer loser of a race                                                        | 409 without a code              | 409 `CONTRACT_OFFER_NOT_ACCEPTABLE`      |
| Add milestone not allowed (not ACTIVE, or an incomplete milestone), including races | 500 or corrupted state          | 409 `MILESTONE_ADD_NOT_ALLOWED`          |
| Finish with an incomplete milestone                                                 | Checked outside the transaction | 409 `CONTRACT_HAS_INCOMPLETE_MILESTONES` |
| Finish of an already finished contract (race)                                       | 409 without a code              | 409 `CONTRACT_ALREADY_FINISHED`          |
| Same reviewer finishing twice in parallel                                           | 500 from the unique constraint  | 409 `REVIEW_ALREADY_SUBMITTED`           |
| Same reviewer finishing again, sequentially                                         | 409 without a code              | 409 `REVIEW_ALREADY_SUBMITTED`           |
| Two parallel `startMeeting`                                                         | Two ACTIVE meetings             | Both get the same meeting                |

Accepted residual risk: after a failed refund the client's money stays captured until a retry, and the other party is not notified by the retry; no work can proceed unpaid because the contract is already cancelled. A reconciliation job that retries refunds of `CANCELLED` contracts is a backlog item. Nothing is incremented at contract creation (counters move at accept), so there is nothing to reverse. Milestones keep their status (no fitting value); every reader of contract status treats `CANCELLED` as neither ongoing nor completed nor payable. The proposal row is unchanged and the cancelled contract still blocks `CONTRACT_EXISTS`, so the same proposal cannot be hired again; another proposal on the released job can. |

Known gaps of item c: releasing the job does not check for other live contracts on the same job (contracts created before ADR 0008 M2 can share a job); the conversation gets an update event but no system message; a refund that fails later at Stripe (after it was created) is not tracked.

Accepted decision: other proposals on a hired job keep their status. There is no `REJECTED` proposal value; the HIRED job lock already blocks acting on them, and releasing the job on decline or withdraw makes them actionable again without any proposal update.

Fee, escrow release and dispute rules stay "to confirm" in `docs/product.md`; no rule was changed here.

## Update 2026-11-19: persisted cancel and refund facts (item c)

Migration `0009_contracts_cancel_refund_facts` adds four nullable columns to `contracts`: `cancelled_at`, `cancelled_by` (`CLIENT` for withdraw, `TALENT` for decline, agency decline included), `refund_id` and `refunded_at`. Checks: `cancelled_by IN ('CLIENT', 'TALENT')`, `(cancelled_at IS NULL) = (cancelled_by IS NULL)` and `refunded_at IS NULL OR status = 'CANCELLED'`. Rows cancelled before this change keep NULLs (legacy rows).

- `cancelPendingContract` sets `cancelled_at` and `cancelled_by` in the same guarded `UPDATE ... WHERE status = 'PENDING'` that cancels; the transaction and the lock are unchanged.
- After the refund call succeeds (still after the commit, no lock held), one guarded statement records it: `UPDATE contracts SET refunded_at = now, refund_id = <id or NULL> WHERE id AND status = 'CANCELLED' AND refunded_at IS NULL RETURNING`. `refund_id` is NULL when `charge_already_refunded` was treated as done. Only the call whose statement returns a row (the winner) runs `emitConversationUpdate` and `sendNotification`, in that order. The recipient follows the stored `cancelled_by`: `TALENT` notifies the client (`CONTRACT_DECLINED`), `CLIENT` notifies the freelancer or agency (`CONTRACT_WITHDRAWN`). A legacy row (`cancelled_by` NULL) gets `refunded_at` but no emit and no notification. The notification carries `eventId = uuidV5("contract-cancelled:" + contractId)`; no other dedupe was added.
- In the cancel path only, a Stripe refund with status `failed` or `canceled` is a refund failure (`payment.refund.failed`, rethrown like a transient failure); `succeeded` and `pending` count as done. Webhook, duplicate, unfulfillable and milestone-funding refunds are unchanged and persist nothing.
- Behavior change: a repeat decline or withdraw after a failed first refund now refunds (idempotent), wins the guarded statement and sends the notification once, which closes the lost-notification gap in "Accepted residual risk" above. A repeat after a fully successful call sends nothing. The transitioning call whose refund fails still answers 500, leaves the contract `CANCELLED` and notifies nobody. Responses are unchanged.
- Crash window: if the refund succeeded but the process died before the guarded statement, the next repeat gets `charge_already_refunded` (done, `refund_id` NULL), wins the statement and notifies. A crash after the statement but before the notification still loses the notification, as before.
- The reconciliation job named in item c is not part of this change; the stored `refunded_at IS NULL AND status = 'CANCELLED'` rows are what it will read.

## Update 2026-11-19: refund reconciliation service (item c, not scheduled)

Migration `0010_contracts_refund_reconciliation` adds `refund_attempts` (integer, not null, default 0, check `>= 0`), `refund_next_attempt_at` (timestamptz, null), `refund_last_error` (text, null) and the partial index `contracts_refund_retry_idx` on `refund_next_attempt_at` `WHERE status = 'CANCELLED' AND refunded_at IS NULL`. `reconcileCancelledContractRefunds({ mode, now?, limit? })` (`contracts.refund-reconciliation.service.ts`, SQL in `contracts.refund-reconciliation.repository.ts`) is the retry logic for the "CANCELLED, `refunded_at` IS NULL" rows. Nothing calls it yet: no cron, no bootstrap wiring, no env variable. It returns `{ scanned, markedDone, refunded, retriedLater, parked, skippedStripeUnavailable, detected, aborted, skipped }`.

- Modes: `detect` reads candidates and Stripe and writes nothing (it logs `refund.reconcile.detected` with the contract id and age); `on` claims, refunds and records. Without a Stripe key the run returns `skipped: 'no-stripe-key'` after one info log and touches nothing.
- Candidates: `status = 'CANCELLED'`, `refunded_at IS NULL`, `refund_attempts < 20`, `cancelled_at` NULL (legacy) or at least 5 minutes old, `refund_next_attempt_at` NULL or due, and a funded first milestone (position 0) that stores a payment intent or a checkout session. Order: `refund_next_attempt_at` NULLS FIRST, then id; default limit 50.
- Claim (mode `on`): one `UPDATE ... SET refund_next_attempt_at = now + 10 minutes WHERE id IN (SELECT id ... FOR UPDATE SKIP LOCKED LIMIT n) RETURNING`, so two runs never take the same row and a crashed run's rows come back after the lease.
- Per row, Stripe is always read before any create: the payment intent is retrieved with `latest_charge`, and `latest_charge.amount_refunded >= amount_received` (with `amount_received > 0`) means the money is already back. The row is then recorded without a refund call and with `refund_id` NULL (`markedDone`). Legacy rows (`cancelled_by` NULL) are recorded the same way and get no notice.
- Otherwise the refund is created by the same helper as the cancel path (`refundContractFirstPayment`, which also rejects Refund status `failed` and `canceled`; `succeeded` and `pending` count as done; `charge_already_refunded` is done with `refund_id` NULL). Key: `refund:<pi>:requested_by_customer` when `cancelled_at` is set and younger than 23 hours (Stripe keeps idempotency keys 24 hours), otherwise `refund:<pi>:requested_by_customer:recon:<refund_attempts at claim time>`.
- Recording uses the cancel path's guarded statement (`markContractRefundedIfUnrecorded`, now also clearing `refund_next_attempt_at` and `refund_last_error`). Only the winner emits the conversation update and sends the notice through the same `notifyCancellation`, with the same payloads and `eventId`; for `TALENT` the emit excludes the freelancer (none for an agency contract, because the declining member is not stored). A failing notice is logged (`refund.reconcile.notify_failed`) and does not undo the record.
- Stripe unavailable (connection error, rate limit, status 429 or 5xx): no attempt is consumed and the lease is released; after 3 consecutive such failures in one run the remaining leases are released and the run stops (`aborted`).
- Permanent codes `charge_not_refundable`, `refund_disputed_payment` and `resource_missing` park the row at once: `refund_attempts = 20`, `refund_last_error` = the code, `refund_next_attempt_at` NULL, log `refund.reconcile.parked` (error level).
- Any other failure: `refund_attempts + 1`, `refund_last_error` = Stripe code, else type, else error name (sanitized, at most 200 characters, never the message), `refund_next_attempt_at = now + min(15 minutes * 2^(attempts before), 24 hours)`. Reaching 20 parks the row as above. A payment intent that cannot be resolved counts as such a failure (`PaymentIntentMissingError`).
- A parked row (attempts 20) never returns to the claim query on its own. Operator reset after the cause is fixed: `UPDATE contracts SET refund_attempts = 0, refund_next_attempt_at = NULL, refund_last_error = NULL WHERE id = '<contract id>' AND status = 'CANCELLED' AND refunded_at IS NULL;`. Only `refund_attempts = 0` is required; the other two columns just make the row due at once.
- Logs: one `refund.reconcile.run` info line per run (only when something was scanned or the run aborted), `refund.reconcile.failed` (warn) per retried failure, no PII.

## Consequences

- Races on these transitions end in a coded 409 instead of a 500 or silent corruption. Losers must not notify or emit.
- The contract row lock serializes add, finish and the finish-side review for one contract; contention is per contract.
- The code field is optional in error bodies; clients must tolerate its absence on older errors.
- Verification: real-Postgres tests with a lock holder (`docs/test-plans/api-state-transitions.md`) and a mutation check. Of 15 mutation runs, 11 were killed and 4 survived as equivalent (redundant guards behind another guard in the same transaction): 4a, 4b, 9a, 9c. The index-drop and non-transactional `startMeeting` mutations were not run (the first needs a DB change; the index is exercised by the two meetings race tests).
