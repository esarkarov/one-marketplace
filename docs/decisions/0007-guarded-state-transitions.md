# 0007: Guarded state transitions

Status: accepted (Stage 5d). Extends the Stage 5c pattern (meeting end, milestone review). Does not change ADR 0005.

## Context

Several status changes in `contracts.service.ts` and `meetings.service.ts` read a row, decided in JavaScript, then updated by id only. Two requests could both pass the read and both write: a second submit or finish worked on a stale state, a milestone could be added to a contract that was finishing, and two `startMeeting` calls could create two ACTIVE meetings. Races surfaced as 500s or as corrupted state.

## Decision

- Every status transition is one guarded conditional `UPDATE ... WHERE status = <expected> ... RETURNING`. Zero rows means a lost race or an invalid state, and the service answers 409 with a code.
- A change that touches several tables runs in one transaction. Notifications, socket/SSE emits, Stripe calls and queue publishes happen only after commit.
- The Stage 5c inline pattern is reused in each service. There is no shared helper. `payout-state.ts` stays payouts-only (ADR 0005).
- `ApiError` gained an optional `code`. `error.middleware.ts` serializes it as `code` in 4xx bodies only when set (5xx bodies never carry it). Only the 409s of the transitions below (submit, accept, add, finish), including their sequential pre-checks, set a code; unrelated errors are not retrofitted.

### Why add and finish take a lock

A `NOT EXISTS` subquery inside the `UPDATE` does not see rows committed after the statement's snapshot, so a finish could complete a contract while a concurrent add commits a new incomplete milestone. Both operations therefore lock the contract row `FOR UPDATE` first and check the milestone state in a separate statement, which takes a fresh snapshot after the lock is granted. The test "serializes an add behind a finish that already read its milestone check" and mutation checks 5 and 6 cover this.

### Submit

Resubmitting an `ACTIVE`, funded milestone stays allowed (changes requested, then work sent again). A concurrent double submit therefore equals two sequential resubmits and is not an error.

### startMeeting

- Invariant: at most one ACTIVE meeting per `conversation_id`. It is derived from the early return in `startMeeting` for an existing ACTIVE meeting.
- It is enforced by the partial unique index `meetings_one_active_per_conversation_unique` (`drizzle/0003_brave_legion.sql`, `WHERE status = 'ACTIVE'`). The migration does not fix data. The maintainer reports that existing dev data was checked and has 0 violations.
- One transaction: meeting insert, `MEETING_STARTED` system message through `postSystemEventMessage` with `{ executor: transaction }`, then `message_id`. The emit runs after commit; its failure is logged (`task.meeting.emit_failed`) and does not fail the start.
- On `23505` for that index, the existing ACTIVE meeting is returned. The Daily room created by the loser is not deleted; it is logged as `task.meeting.room_orphaned` with the room name.

## Client-visible changes

| Case                                                                                | Before                          | Now                                      |
| ----------------------------------------------------------------------------------- | ------------------------------- | ---------------------------------------- |
| Submit on a milestone that is not ACTIVE and funded (including races)               | Update by id, no check          | 409 `MILESTONE_NOT_SUBMITTABLE`          |
| Accept offer loser of a race                                                        | 409 without a code              | 409 `CONTRACT_OFFER_NOT_ACCEPTABLE`      |
| Add milestone not allowed (not ACTIVE, or an incomplete milestone), including races | 500 or corrupted state          | 409 `MILESTONE_ADD_NOT_ALLOWED`          |
| Finish with an incomplete milestone                                                 | Checked outside the transaction | 409 `CONTRACT_HAS_INCOMPLETE_MILESTONES` |
| Finish of an already finished contract (race)                                       | 409 without a code              | 409 `CONTRACT_ALREADY_FINISHED`          |
| Same reviewer finishing twice in parallel                                           | 500 from the unique constraint  | 409 `REVIEW_ALREADY_SUBMITTED`           |
| Same reviewer finishing again, sequentially                                         | 409 without a code              | 409 `REVIEW_ALREADY_SUBMITTED`           |
| Two parallel `startMeeting`                                                         | Two ACTIVE meetings             | Both get the same meeting                |

## Remaining unguarded or out of scope

| #   | Item                                     | Reason                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a   | Agency double review                     | Two agency teammates finishing or reviewing in parallel can both pass the early `existingReview` check. `reviews_contract_reviewer_unique` does not include `agency_id` or reviewee, so it does not catch different reviewers. The contract lock serializes only when one of them finishes the contract. Closing it needs an `existingReview` re-check inside the lock or a schema change. Deferred. |
| b   | HIRED gap                                | Nothing writes job status `HIRED` after an offer is accepted. It is only read at `proposals.service.ts:250`, and the `ne(job_posts.status, "HIRED")` guards in `jobs.service.ts` (update and delete) never block. A product decision, to confirm in `docs/product.md`.                                                                                                                               |
| c   | Decline or withdraw                      | No such transitions exist in the API.                                                                                                                                                                                                                                                                                                                                                                |
| d   | Double-paid checkouts                    | The second webhook is ignored, but the client was charged twice. Follow-up.                                                                                                                                                                                                                                                                                                                          |
| e   | Loser of the two-party finish race       | Gets 409 and no review is recorded, although they could review afterward.                                                                                                                                                                                                                                                                                                                            |
| f   | Proposal past INTERVIEWED                | A proposal never moves beyond INTERVIEWED.                                                                                                                                                                                                                                                                                                                                                           |
| g   | `updateProposal` SHORTLIST flag          | Idempotent and harmless.                                                                                                                                                                                                                                                                                                                                                                             |
| h   | Daily room on a lost `startMeeting` race | Orphaned and only logged.                                                                                                                                                                                                                                                                                                                                                                            |
| i   | `job_posts.milestones` across contracts  | `addContractMilestone` re-reads the array under the contract lock only. A job can have several contracts, so concurrent adds on two contracts of the same job can lose one JSON entry (`total_budget_cents` uses a SQL increment and is unaffected). Fix: `FOR UPDATE` on the `job_posts` select or an atomic `jsonb` append. Follow-up.                                                             |

Fee, escrow release and dispute rules stay "to confirm" in `docs/product.md`; no rule was changed here.

## Consequences

- Races on these transitions end in a coded 409 instead of a 500 or silent corruption. Losers must not notify or emit.
- The contract row lock serializes add, finish and the finish-side review for one contract; contention is per contract.
- The code field is optional in error bodies; clients must tolerate its absence on older errors.
- Verification: real-Postgres tests with a lock holder (`docs/test-plans/api-state-transitions.md`) and a mutation check. Of 15 mutation runs, 11 were killed and 4 survived as equivalent (redundant guards behind another guard in the same transaction): 4a, 4b, 9a, 9c. The index-drop and non-transactional `startMeeting` mutations were not run (the first needs a DB change; the index is exercised by the two meetings race tests).
