## Part A. Open questions closed

### A1. Redis errors in the auth and connects middleware [V]

- `isAccountAvailable` calls `redis.get` (R/modules/auth/middleware/auth.middleware.ts:50) and `redis.setEx` (:69) with no try/catch.
- `isAuthenticated`, `identifyAccount` and `resolveAccountRole` reach it through `loadRequestAuth` (:149,175,202), outside `verifyClaims`' try (:129-143). The raw error goes `asyncHandler` (middleware/utils/async-handler.utils.ts:9-13) to `errorHandler` (middleware/error/error.middleware.ts:42-43,59-63,80-86): **HTTP 500**, body "Internal server error.", log message "Unhandled request error", `eventName: "system.request.failed"`.
- `authenticateAccount` (:80-107) wraps the call in try and maps any non-ApiError to **401** "Authentication token is invalid or expired." Its callers: auth controller (modules/auth/controllers/auth.controller.ts:47) and the Socket.IO handshake (modules/messaging/messaging.socket.ts:79). So during a Redis outage `/auth/status` and socket connects answer 401, which a client reads as "signed out".
- Connects: `availableConnects` (modules/connects/middleware/connects.middleware.ts:10-43) is mounted by `connects.route.ts:21` for GET `/`, GET `/history`, POST `/checkout`. Freelancer branch: `redis.get` :20, `expire` :24, `setEx` :35, no try. Same 500 and `system.request.failed`. Non-freelancers skip Redis (:14-17).
- Invalidation is safe: `infrastructure/cache/account-auth.cache.ts:6-20` catches, warns `auth.cache.invalidate_failed`, does not rethrow; the stale entry lives up to 600 s (30 s negative).
- Redis client behavior behind this (A6): default command timeout 5 s, offline queue on, and the app's reconnect strategy ends the client permanently after 10 attempts.

### A4. Dead-letter queue [V]

- Declared: `notifications.dead` bound to fanout `notifications.dlx` (R/infrastructure/events/notification.topology.ts:13-14,23-27,35-36).
- Nothing consumes or alerts on it. The only operational text is manual: inspect in the management UI on 15672, read `x-death`, purge by hand (docs/test-plans/api-rabbitmq.md:40-47; ADR 0004:68); ADR 0006:30-32 says "drained or purged". ADR 0024:54 alerts only on `queue.publish.skipped` and `queue.publish.failed`. No retention, TTL, replay tool or alert in `infra/` (docker-compose.yml:50-63 has only a healthcheck) or `.github/`.
- Related [D]: for quorum queues `basic.nack` does not increment the delivery-count, and from RabbitMQ 4.3 requeues by nack do not count toward the delivery limit at all https://www.rabbitmq.com/docs/quorum-queues. The consumer requeues with nack (inv. §4). **[I]** On the 4.4 broker used here, `x-delivery-limit` 5 may therefore not bound the nack-requeue loop; the in-memory counter (reset on restart) would be the only bound. Verify on the real broker before relying on either.

### A5. Clerk usage and display names [V]

- Per-request `getUser` sites: (a) `admin.listings.service.ts:35-61` `clerkNames`, `Promise.all` per unique authId, no timeout, no cache, fetches name, `emailAddresses[0]` (name fallback, :50-51) and `imageUrl`; called by accounts (:76), proposals (:135), contracts (:184), transactions (:269), not job posts (:110); input is `offset + limit + 1` (:69), so Clerk calls grow with offset. (b) `auth.display.service.ts:57` `syncAccountDisplay`, 2 s timeout, on profile save and invitation answer (client.service.ts:67, freelancer.profile.service.ts:222, agency.profile.service.ts:280,420, agency.invitations.service.ts:318). (c) `auth.service.ts:28` signup, 300/600 ms retries. (d) `freelancer.earnings.service.ts:138` certificate GET, `fullName` only.
- Authentication itself uses `verifyToken` only, no user fetch (auth.middleware.ts:95,131).
- Stored display fields: `accounts.email`, `display_name`, `avatar_url` (auth/models/auth.model.ts:15-17), read by `findAccountDisplays` (one batched query, no Clerk). Denormalized search text in `freelancer_metadata.search_text` and `agency_metadata.search_text` (ADR 0019).

### A6. Library defaults [V], installed versions

express 5.3.0, body-parser 2.4.0, engine.io 6.6.11, socket.io 4.8.4, redis 6.3.1 (@redis/client 6.3.1), pg 8.23.1 / pg-pool 3.14.0.

- `express.raw` default `limit` 102400 bytes = 100 kb (body-parser/lib/utils.js:46-47); the app passes no limit (R/app.ts:24). Oversize gives 413. Webhook bodies are small, so low risk.
- Socket.IO uses engine.io defaults: `maxHttpBufferSize` 1e6 (1 MB), `pingInterval` 25000, `pingTimeout` 20000 (engine.io/build/server.js:48-51); the app passes only `cors` (messaging.socket.ts:87, re-read). The 20 MB JSON route for messages is HTTP; socket payloads are limited to 1 MB.
- node-redis: command `timeout` default 5000 ms (client/index.js:466; defaults.js:5); offline queue **enabled** (`disableOfflineQueue` unset, checked at index.js:1132); `commandsQueueMaxLength` unset (no cap); `socket.connectTimeout` 5000 ms (socket.js:45); library default reconnect strategy retries forever (socket.js:429-440).
- **The app overrides the strategy** (R/infrastructure/cache/redis.client.ts:9-15, re-read): after 10 retries it returns an Error. The library then sets `#isOpen=false`, emits `terminated`, and every later command rejects with `ClientClosedError` (socket.js:150-156; client/index.js:1129,1250). No app code calls `connect()` again (inv. §3). **[I]** After roughly 15 s of Redis downtime (delays 100,200,400,800,1600,3000 x4) the API stays broken for every authenticated route until the process restarts. Readiness answers 503, which only helps if an orchestrator acts on it.
- During those 15 s queued commands wait up to 5 s each, so requests hang up to 5 s before the 500.
- pg: pool `max` 10, `idleTimeoutMillis` falls back to 10000 in pg-pool unless set, `connectionTimeoutMillis` unset means no timeout, `query_timeout` and `statement_timeout` default false (pg-pool/index.js:89,98-99,206; pg/lib/defaults.js:65,76). The app sets 10 s, 30 s, 60 s (inv. §2).

### A7. User-keyed limiters run after authentication? [V]

Yes on all 8 routes: messaging.route.ts:44-46; jobs.route.ts:51-52,95-96; freelancer.route.ts:71-72; agency.route.ts:129-130,198-199,205-206,224-225 (auth middleware then limiter). Key: `request.auth?.userId`, else `authClaims?.userId`, else `ipKeyGenerator(ip)` (user-rate-limit.middleware.ts:19-34). Windows: message 120 and content 30 per 15 min, invites 20 per hour (rate-limit.constants.ts:1,7-11). Caveat: `verifyBearerToken` routes run the limiter before any account or role check, so a valid-token holder without an account still consumes its own quota; a bad token gets 401 before the limiter. Memory-store fallback is per process (inv. §3).

## Part C. Deep dives

### C1. Observability: OpenTelemetry

Maturity (versions from `pnpm view`, read only, 2026-11-21; all declare `engines.node >=22.15.0`, so Node 26.13 is covered [V]): `@opentelemetry/sdk-node` 0.301.2, `instrumentation-http` 0.301.2, `instrumentation-express` 0.73.0, `instrumentation-pg` 0.78.0, `instrumentation-amqplib` 0.72.0, `instrumentation-redis` 0.73.0. All are 0.x: the API can still change between minor versions [I].

- Express 5: the contrib README for `instrumentation-express` lists `>=4.0.0 <6`; the older range excluded 5 and the request was closed through a later change https://github.com/open-telemetry/opentelemetry-js-contrib/tree/main/packages/instrumentation-express. Known issue: with both express and router instrumentations, Express 5 layers yield duplicate "middleware - patched" spans https://github.com/open-telemetry/opentelemetry-js-contrib/issues/3881. Enable `express` or `router`, not both [D].
- ESM: the API is ESM; the getting-started page says ESM apps need a loader hook and the SDK file is loaded first (`node --import ./instrumentation.mjs`) https://opentelemetry.io/docs/languages/js/getting-started/nodejs/. An issue records Express routes missing under ESM without the hook https://github.com/open-telemetry/opentelemetry-js-contrib/issues/3834. Plan on `--import` plus the hook, and test that route names appear.
- `pg`: instrumentation targets the `pg` driver, which Drizzle uses (inv. §2) [I]. `redis`: whether `instrumentation-redis` 0.73.0 covers node-redis 6.3.1 is **[A] unverified**; read its README supported range first. `amqplib`: the app uses `amqp-connection-manager` on top of `amqplib` [V inv. §4]; instrumentation of the underlying library is expected to work but **[A] unverified**.
- Export: OTLP over HTTP to a local collector, default `http://localhost:4318/v1/traces` and `/v1/metrics`; set the path when configuring endpoints in code https://opentelemetry.io/docs/languages/js/exporters/ and https://opentelemetry.io/docs/languages/js/getting-started/nodejs/. A zero-code path via environment variables exists https://opentelemetry.io/docs/zero-code/js/.
- Collector and backend: for learning, a collector with a debug exporter plus one local viewer container in `labs/` (not in `infra/docker`, which is shared) [I].
- Correlation: today `x-request-id` is accepted and echoed (request-id.middleware.ts:4-18) but not propagated to Stripe, Daily, ImageKit or RabbitMQ (inv. §8). With the SDK, W3C trace context is injected into outbound HTTP; propagation APIs are documented https://opentelemetry.io/docs/languages/js/propagation/. For RabbitMQ, put `traceparent` and `requestId` in AMQP message headers rather than the zod envelope (`version: z.literal(2)`, notification.envelope.ts:46), so no schema bump is needed [I]; the amqplib instrumentation is expected to do this itself [A]. Add `trace_id` to pino lines via a mixin [I].
- Existing log event names that map to counters [V names]: `system.request.failed` (5xx), `redis.error`, `auth.cache.invalidate_failed`, `rate_limit.store.error`, `webhook.inbound.dedupe_unavailable`, `queue.publish.skipped`, `queue.publish.failed`, `payment.refund.unrecoverable`, `payment.refund.no_payment_intent`, `payment.orphan.detected`, `payment.orphan.truncated`, `payment.payout.notification_failed`. Gauges that need new code: DLQ depth (management API), pool `waitingCount`, cron last-success time.
- Risks: auto-instrumentation wraps hot paths; keep it behind an env flag; log redaction does not apply to span attributes, so `db.statement` could capture values (check the pg instrumentation's statement options before enabling) [A]. SQL text with PII or money is a leak risk.
- Cost/benefit: value is high only if there is a place to look at traces. Hosting unknown, so treat as Learning Experiment (D2).

### C2. HTTP Idempotency-Key

Status: an IETF HTTP API working-group Internet-Draft exists, `draft-ietf-httpapi-idempotency-key-header`; the header is a Structured Header string, key uniqueness is defined by the resource owner, and example errors are 400 (missing key), 422 (same key, different request), 409 (original still in flight) https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-06 and https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html. Draft 06 is shown expired there; treat it as a convention, not a standard [D].

- Which routes: only POSTs that move money or create a paid resource: `POST /connects/checkout`, contract and milestone checkout starts (contracts.checkout.service.ts:332,340,401 send no Stripe key; connects.service.ts:171,255), possibly proposal submit (spends connects; unique-constraint protection **not verified** [A]). Everything else is already guarded by state transitions (ADR 0007).
- Verified benefit is small [I]: a duplicate checkout start creates a second Checkout Session, which costs nothing until paid, and a duplicate payment is refunded by the webhook guards (A2). The gain is UX and cleanliness, not money safety.
- Header: `Idempotency-Key: <opaque string, 16-64 chars, [A-Za-z0-9._-]>`, same charset rule as the request id. Optional at first (absent = today's behavior), then required on the listed routes.
- Storage: new Postgres table `http_idempotency` (account id, route template, key, SHA-256 of canonical body, status IN_PROGRESS|DONE, response status, response body, created_at, expires_at), unique on (account id, route template, key). Postgres rather than Redis because the answer must survive Redis loss (A1) and be committed with the business effect. Migration through `/db-change` [per repo rules].
- Scope: per account (public id, never Clerk id) and per route template, so the same key on another route does not collide.
- Flow: claim by `INSERT ... ON CONFLICT DO NOTHING`; inserted = run handler; conflict = read row: DONE and same fingerprint = replay stored status and body with `Idempotent-Replayed: true`; DONE and different fingerprint = 422 coded; IN_PROGRESS = 409 coded with `Retry-After`.
- Concurrent duplicates: the unique index serializes them; the loser never runs the handler.
- Expiry: 24 h, aligned with Stripe's minimum key retention [D] https://docs.stripe.com/api/idempotent_requests; cleanup by an existing cron-style sweep (retention of other tables is also undefined, inv. §5).
- Stripe interplay: do not forward the client key. Derive `Idempotency-Key` for Stripe as `<route>:<accountId>:<clientKey>` so a retried request after a crash hits the same Stripe operation (Stripe: retry network errors with the same key and parameters inside the retention window, different parameters error) https://docs.stripe.com/api/idempotent_requests. Today the SDK generates a per-request key that is not stored (inv. §6), so only the SDK's internal retries are protected.
- Failure modes: (1) crash after claim, before completion: row stuck IN_PROGRESS; needs a lease timeout (for example 60 s) after which a retry may re-claim, which is safe only because the Stripe key is stable; (2) response stored but not delivered: replay solves it; (3) non-deterministic bodies (timestamps) break the fingerprint, so hash only validated fields from `getValidated`; (4) 5xx responses should not be stored, so a retry re-runs; (5) storage growth; (6) key reuse across accounts is impossible by scope.
- Fit with repo rules: a middleware after authentication and `validate`, response schemas gain 409 and 422 entries, OpenAPI regenerates, contract tests per route (ADR 0011/0012). The api-client and web-core would need to send keys, so frontend work is part of the cost.

### C3. Process roles and scaling

Verified current state: one process runs HTTP, Socket.IO, SSE, the notification consumer and three crons (inv. §7). Each cron is already safe with several instances: payouts claim with `FOR UPDATE SKIP LOCKED` and reclaim stuck claims after 15 min (payouts.repository.ts:58-60,73-93; payouts.state.ts:10); refund reconciliation uses a DB lease and materialized claim (ADR 0023); orphan detection is read-only. The consumer is a competing consumer with idempotent insert. [I] So running N processes today duplicates cron attempts but not money effects. `sweepUnnotified` concurrent runs rely on `onConflictDoNothing` plus an idempotent mark [I].

What breaks with N API instances [V unless marked]:

- Socket.IO has no adapter (messaging.socket.ts:87): presence, typing and `conversation:update` reach only clients on the same instance; with HTTP long-polling, the docs also require sticky routing or "Session ID unknown" 400s occur, and a Redis adapter (or other) is needed for cross-node delivery [D] https://socket.io/docs/v4/redis-adapter/ and https://socket.io/docs/v3/using-multiple-nodes/. WebSocket-only transport removes the sticky need [D].
- SSE registries are in-memory Maps (notifications.sse.ts:3-4). `pushStoredNotification` after commit reaches only the instance that handled the request; the consumer's push reaches only the instance that consumed. Persisted rows are fine; the realtime hint is lost [I]. ADR 0024:64 already accepts "no replay".
- Rate-limit memory fallback is per process, so the effective limit multiplies by N only while Redis is down.
- Redis client termination (A6) affects every instance independently.
- Admin session is a stateless HMAC token (inv. §9), no problem.

Minimal design if roles are wanted [I]: env `PROCESS_ROLE=api|worker|all`, default `all` (no behavior change). `api` skips crons and consumer; `worker` skips `listen`, Socket.IO, SSE pusher registration. Moves to worker: payout cron, refund cron, orphan cron, consumer. Problem: the consumer's SSE push needs the API process, so either keep the consumer in `api`, or add a fan-out (Redis pub/sub or Postgres LISTEN/NOTIFY) first. That is the real cost, not the role switch. Worker still needs a health port or readiness check for the orchestrator [A]. Shutdown order (bootstrap/shutdown.ts:146-213) has to be split per role.

What not to do: Node `cluster` helps CPU scaling of one server across cores https://nodejs.org/api/cluster.html but multiplies the same in-memory-state problems on one host [I].

Recommendation: do not split roles until (a) hosting is known and (b) a second API instance is actually planned. First fix row 31 and add a Socket.IO adapter spike when scale-out is on the table.

### C4. Account-display read model and CQRS boundaries

Three options compared:

|                           | Do nothing                                                                                            | Cache-aside (Redis)                                          | Webhook projection                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------- |
| Behavior today            | stored columns refreshed on profile save with 2 s Clerk timeout (A5); staleness accepted (ADR 0019:6) | would add a second copy, with the Redis failure problem (A1) | updates stored columns when the Clerk profile changes       |
| Fixes admin Clerk fan-out | no                                                                                                    | yes, partly (warm cache)                                     | yes, if admin reads stored columns                          |
| New moving parts          | none                                                                                                  | keys, TTL, invalidation                                      | public route, signature check, idempotent handler, backfill |

Key insight [V]: the read model already exists. `accounts.display_name`, `avatar_url`, `email` and the two `search_text` columns are a denormalized projection (ADR 0019); `findAccountDisplays` reads it with one batched query. **The admin fan-out (row 43) is fixed by switching admin listings to `findAccountDisplays`, with no webhook and no cache.** Cost: admin shows the stored name and possibly a stale email; for admin email, keep a lazy Clerk call only on a detail view [I].

If the webhook is built (Learning Experiment, D3):

- Events: `user.created`, `user.updated`, `user.deleted` [A: names and Svix delivery headers must be taken from Clerk docs, which are outside this stage's allowed sources].
- Route: raw body registered before `express.json`, like the Stripe and Daily routes (AGENTS.md "Rules"), signature verified, 2xx fast.
- Idempotent consumer: store the delivery id in a small table with a unique key (the pattern Stripe documents for its own events [D] https://docs.stripe.com/webhooks), or make the update naturally idempotent (set absolute values).
- Ordering and staleness: events can arrive out of order; apply only if the event's `updated_at` is newer than a stored `display_synced_at` (new column; migration), otherwise ignore [I].
- Ownership problem [I]: `accounts` belongs to `auth` (layer 0) but `search_text` columns belong to freelancer (L2) and agency (L3); layer 0 cannot import upward, and cross-module writes must be owner functions (ADR 0014 s.11). So the handler lives in a higher layer or publishes an internal event that owners subscribe to. This is the largest design cost.
- Backfill: a script paging Clerk users, run by the user (agents may not run `services/api/scripts/*.ts`); the existing `backfill-search-text.ts` rebuilds search text from stored values only (AGENTS.md).
- Failure modes: webhook outage means staleness returns to today's level (self-healing on next profile save); a bad handler can overwrite correct names, so keep the 2 s timeout fallback and never write placeholders over real values; user deletion must not hard-delete accounts [A].
- Lightweight CQRS boundaries: write side = Clerk (identity source of truth) and the owning modules' write paths; read side = denormalized columns read only through `findAccountDisplays`; synchronization = one function in auth, called after commit and never inside a transaction (`syncAccountDisplay`, AGENTS.md); no event store, no second database, no separate query service. Stop there.

### C5. External-call resilience

| Integration      | Today [V]                                                                                                                              | Recommendation                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Stripe           | timeout 30 s, SDK retries default 2 (stripe.client.ts:6-14; inv. §6), keys on refunds and transfers; creates send SDK per-request keys | keep; if lowering the timeout, do it per call type; add idempotency keys derived from business ids on checkout creates (C2)                    |

| Daily            | raw `fetch`, no timeout, no retry, no key; non-ok throws plain Error (500)                                                             | `AbortSignal.timeout(5-10 s)`; map failures to 502 like Stripe; **no retry on POST room creation** (no key); the join-token GET may retry once |
| ImageKit         | no timeout or retry in code                                                                                                            | timeout; **no automatic retry on uploads** (a retried upload can create a duplicate file) unless the file name is deterministic [A]            |
| Redis            | default command timeout 5 s (A6)                                                                                                       | set a short `commandOptions.timeout` for cache reads and fail open (row 31)                                                                    |

- Safe retries: GET and PUT-by-key operations; Stripe calls carrying an idempotency key; publishes with a deterministic message id. Never: Daily room creation, ImageKit upload, any Stripe create without a stable key.
- Breaker libraries (read-only `pnpm view`): `opossum` 10.0.0, `engines.node ^26 || ^24 || ^22`, package last modified 2026-08-03, EventEmitter-based, stats built in. `cockatiel` 4.0.0, `engines.node >=22`, last release 2026-05-26 (3.1.3 was 2024-05-04), provides timeout, retry, circuit breaker and bulkhead as composable policies. Both are maintained and list Node 26 support or a floor below it [V]. I have not read their code; API shape claims are [A]. Prefer cockatiel if one library should cover timeout, retry, breaker and bulkhead; prefer opossum if only a breaker around a function is needed.
- Breaker state is per process and the API is a single instance, so a breaker adds little beyond timeouts [I]. Order: timeouts first (rows 31, 32), breaker only after metrics show repeated slow failures.
- Pool isolation as bulkhead: a second `pg.Pool` (for example max 3) for crons and the consumer would keep the 10-connection HTTP pool free, at the cost of 3 more server connections and a second `DbExecutor` source [I]. No evidence of starvation exists (inv. §11 has no measurements); do it after a load test shows queueing (`pool.waitingCount`).

### C6. Fastify, BFF and microservices

Evidence from the inventory that gives no reason today:

- Framework: Express 5.3.0 is current in the repo (A6); no profiling, benchmark or load test exists (inv. §11), so no claim that the framework limits anything can be supported. The cost of leaving is concrete: a custom OpenAPI generator that introspects the Express router (openapi/document.ts:27-47), 13 architecture tests plus 4 route checks, `validate` and `getValidated` middleware, 102 operations with contract tests. Second-framework adoption would be a rewrite of that layer for no verified gain.
- BFF: Next.js route handlers and proxies already exist per app (inv. §10). The open problem is that freelancer and agency dashboards make 52 and 53 raw `fetch` calls without the typed client (inv. §10); finishing the migration plan removes it. A BFF would add a hop and a second contract.
- Microservices: the modular monolith already enforces layers, one table owner per table and a read-only cross-module allowlist (59 entries, inv. §1), which keeps extraction possible without paying for it. There is one database, one deployable, and no measured independent scaling need. Splitting would turn the 59 cross-module reads and in-transaction owner functions into network calls and sagas.

Evidence that would change the answer (collect before deciding):

1. Fastify: a load test on production-like hardware showing the HTTP layer, not Postgres, Stripe or serialization, dominating CPU at the target traffic; plus a plan for the OpenAPI and test tooling.
2. BFF: measured screens needing many API round trips, or clients needing different shapes that the API cannot serve with one endpoint; or a security need to keep tokens out of the browser.
3. Microservices: a module with clearly different scaling, failure isolation or compliance needs (for example payments or realtime) proven by metrics; separate teams or release cadence; incidents caused by shared fate.
4. For all three: production hosting, traffic and team size (questions below).
