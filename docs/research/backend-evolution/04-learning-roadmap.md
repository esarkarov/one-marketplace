### 1.3 Resilience client wrapper

**Decision:** write a small own wrapper (no dependency) so the mechanics are learned; compare cockatiel and opossum in Track 4.1 (eval. C5 versions). The wrapper covers timeout and bounded retry only; breaker and bulkhead are explicitly absent and the API has no placeholder for them.

**Flag:** `EXTERNAL_CALL_RETRIES=on|off` (default `on`; `off` = one attempt, timeouts stay).

**Files:**

- `R/infrastructure/utils/external-call.utils.ts` (+ `.utils.test.ts` beside it; utils files must be `*.utils.ts`), types in `R/infrastructure/types/external-call.types.ts` (types files must be `index.ts` or `*.types.ts`), policies in `R/infrastructure/constants/index.ts` as `EXTERNAL_POLICIES` (constants file rule).
- API: `callExternal<T>(policyKey, run: (signal: AbortSignal) => Promise<T>, options?: { signal?: AbortSignal }): Promise<T>`. A policy is `{ target, operation, timeoutMs, idempotent: boolean, retry?: { max, baseMs, maxMs, totalBudgetMs } }`; the type forbids `retry` unless `idempotent: true`, and a unit test asserts the invariant over the whole table.
- Per attempt signal: `AbortSignal.any([AbortSignal.timeout(timeoutMs), options.signal])`. `AbortSignal.timeout` and `AbortSignal.any` are documented [D] https://nodejs.org/api/globals.html (Node 26.13.1). The page does not state the abort reason's error name, so classify a timeout by "the timeout signal fired and the caller's signal did not", never by error name.
- Backoff: full jitter, `random(0, min(maxMs, baseMs * 2^attempt))`, random source injectable; stop when `totalBudgetMs` would be exceeded. Retryable: timeout, network error codes (ECONNRESET, ECONNREFUSED, ETIMEDOUT, EAI_AGAIN, `UND_ERR_*`), numeric `status` in 429, 502, 503, 504; never other 4xx. Stripe's own rule is the model: retry with a stable key only, [D] https://docs.stripe.com/api/idempotent_requests (carried from eval. C2).
- Errors: `ExternalCallError { policyKey, kind: "timeout"|"network"|"status"|"aborted", status?, attempts, cause }`. `DailyRequestError` from item 32 stays and wraps it (same `status`, `timedOut` fields) so the 502 mapping at meetings.service.ts:74 is unchanged.
- Observer: `registerExternalCallObserver(fn)` (same listener idea as the log hook); called once per call with `{ policyKey, outcome, attempts, durationMs }`. Item 1.1 subscribes it to the histogram; if 1.1 is not merged, the observer has no subscriber. Logs: `external.call.failed` (warn, `{ policy, outcome, attempts, status }`, never URLs, headers or bodies) once per failed call; `external.call.retry` (debug).
- Policies to adopt in this item: `daily.createRoom` (8 s, `idempotent: false`, no retry: no key exists, eval. C5), `daily.createToken` (8 s, retry max 1; confirm in daily.client.ts that token creation has no room side effect [A]), other Daily reads (same as createToken), `clerk.signup.getUser` (replaces the ad hoc 300 ms and 600 ms retries at auth.service.ts:24-34; keep equal delays through the policy so tests keep their meaning), `clerk.syncDisplay` (2 s, no retry; replaces `auth.display.service.ts:48-57`'s own timeout). **Not adopted here:** Stripe and ImageKit (Stripe's SDK retries internally and the money path is out of scope; ImageKit uploads must not retry, eval. C5). Listed as 4.1 follow-ups.
  **Tests:** success first try; retry then success with fake timers; non-idempotent never retries; exhaustion gives `ExternalCallError` with `attempts`; caller abort ends at once with kind `aborted`; jitter within bounds with injected random; total budget stops early; observer called exactly once; policy-table invariant; Daily client tests and meetings contract test unchanged in outcome; signup tests updated to the policy. **Mutation check:** let a non-idempotent policy retry and see the invariant test fail.
  **DoD:** tests, ADR 0028 (options: library now vs own wrapper, retry classes table), `docs/frontend-integration-notes.md` unchanged unless a status code changes, openapi hash unchanged. **Reverse:** flag off or revert. **Risk:** signup and meeting join paths gain a retry; keep `max` low.

### 1.4 Outbox for the 8 direct-publish kinds

**Label:** adopted for learning. ADR 0024 already covers must-not-lose kinds through in-transaction `insertNotification`; this item routes the remaining 8 through a relay instead, which is the pattern being learned. The ADR must say the 8 kinds are best-effort by product choice and would be needed only if loss is observed (03 trigger).

**Flag:** `OUTBOX_MODE=off|shadow|on` (default `off`). `off`: `enqueueNotification` inserts nothing and returns `false`; callers send directly as today. `shadow`: row inserted in the business transaction, function returns `false` so the caller still sends directly after commit; the relay also publishes; the consumer's unique `event_id` absorbs the duplicate (`insertNotificationIfNew`, notification-store.repository.ts:23 [V]). `on`: row inserted, returns `true`, no direct send. Treat any mode as `off` when RabbitMQ is not enabled (`isRabbitEnabled()`), so rows never pile up without a broker.

**Module (new, layer 0):** `R/modules/outbox/`: `outbox.cron.ts` (relay loop), `index.ts`, `models/outbox.model.ts`, `repositories/outbox.repository.ts`, `services/outbox.service.ts`, `constants/outbox.constants.ts`, `types/outbox.types.ts`, `tests/`. Required edits to architecture facts: layer map in `R/test/architecture/import-boundaries.test.ts:24-41` and `docs/architecture.md:34` (layer 0 gains `outbox`), `table-ownership.ts` (`outbox_events: "outbox"`), table file path rule (`models/outbox.model.ts`). Relay must live in the module, not `infrastructure/events`: SQL is banned outside repositories and infrastructure may not import modules [V explorer: repository-sql.test.ts:41, import-boundaries.test.ts:134]. The module imports `sendNotification`/`isRabbitEnabled` from infrastructure (allowed direction).

**Table `outbox_events` (migration `0011` through `/db-change`, local Docker only):** `id uuid pk default gen_random_uuid`, `event_id uuid not null unique` (the envelope id), `payload jsonb not null` (a `NotificationInput` without `eventId`), `traceparent text null`, `status text not null` in `PENDING|PUBLISHING|PUBLISHED|DEAD`, `attempts integer not null default 0`, `next_attempt_at timestamptz not null default now()`, `claimed_at timestamptz null`, `last_error text null` (sanitized, 500 chars), `created_at`, `published_at`. Partial index `(next_attempt_at) WHERE status IN ('PENDING','PUBLISHING')` and an index on `(status, published_at)` for retention. Money is not stored; payload `metadata` rules from the envelope apply (cents only).

**API of the module:** `enqueueNotification(executor, input: NotificationInput & { eventId: string }): Promise<boolean>`; `sendUnlessQueued(queued: boolean, input): Promise<void>` (calls `sendNotification` when `queued` is false); `startOutboxRelay()`, `stopOutboxRelay()`, `waitForOutboxRelayRun()`, `getOutboxStats()` for gauges. `eventId` is mandatory for all callers, built with `notificationEventId(type, entityId, transition)` (notification-store.event-id.ts:14-25 [V]); the id is now also passed on the direct path, so ids are deterministic in every mode. Per-site entity and transition (agent confirms in code): invitation answered `invitationId:accepted|declined`; welcome bonus `agencyId:welcome-bonus`; contract accepted `contractId:accepted:<recipient kind>` (two sends at contracts.lifecycle.service.ts:559,569); milestone added `milestoneId:added`; completed or review `contractId:completed|review:<recipient>`; proposal received `proposalId:received`; proposal viewed `proposalId:viewed` (a repeat view no longer renotifies; confirm intended in the report).

**Relay (copy ADR 0023's claim shape, inv. §2/§5):** a self-rescheduling `setTimeout` loop (precedent: the consumer's resume timer, notifications.consumer.ts:100; `unref`'d; no `node-cron`, which has no sub-minute tick [A]): idle interval 1 000 ms, immediate re-run when a full batch was found. Claim: `WITH picked AS MATERIALIZED (SELECT id FROM outbox_events WHERE (status = 'PENDING' AND next_attempt_at <= now()) OR (status = 'PUBLISHING' AND claimed_at < now() - lease) ORDER BY next_attempt_at, id LIMIT $batch FOR UPDATE SKIP LOCKED) UPDATE outbox_events SET status='PUBLISHING', claimed_at=now(), attempts=attempts+1 FROM picked WHERE ... RETURNING ...` ([D] https://www.postgresql.org/docs/current/sql-select.html describes `SKIP LOCKED` as suitable for queue-like tables with the "inconsistent view" caveat). Constants: batch 50, lease 60 s, max attempts 10, backoff `min(5 s * 2^n, 10 min)`, retention of PUBLISHED rows 7 days (deleted in the relay tick, batch of 500). Per row: `sendNotification({ ...payload, eventId })`; result `"published"` -> guarded UPDATE `status='PUBLISHED'` `WHERE id=$ AND attempts=$claimedAttempts`; `"failed"` -> guarded retry update (status PENDING, `next_attempt_at`), attempt 10 -> `DEAD` plus error log `outbox.event.dead`; `"disabled"` -> release without counting (warn once). Publishing is confirm-based: confirms mean the quorum queue accepted the message [D] https://www.rabbitmq.com/docs/confirms; the page says nothing on publisher duplicates, so a crash between publish and mark can republish, which the consumer dedupes. [A] verify in notification.publisher.ts that `"published"` is returned only after the confirm. Logs: `outbox.relay.failed` (error), `outbox.relay.lag` (warn when the oldest PENDING row is older than 60 s), `outbox.event.dead` (error, alert on it). Gauges (item 1.1): `outbox.pending`, `outbox.oldest_pending_age_ms`, `outbox.dead`.
**Trace link:** `enqueueNotification` stores the active W3C `traceparent` when telemetry is on, and the relay starts its span as a link to it, so one request-to-delivery trace is possible [I].

**Wiring:** `R/bootstrap/start.ts` after `startNotificationConsumer` (:54-56) and only when mode is not `off` and RabbitMQ is enabled; `shutdown.ts` stops the relay and awaits the in-flight tick inside the drain step (:195-201) before `closeRabbit`.

**Call sites (all 8; each insert must sit in the transaction that performs the business change):** agency.invitations.service.ts:321 (transaction ends :295, move the enqueue inside); agency.profile.service.ts:494 (inside the onboarding branch's transaction, :433); contracts.lifecycle.service.ts:559,569 (`acceptContract`, :554, owns its own transaction: add the enqueues there or return a descriptor; **if this needs a change to money SQL, stop and report**); :727 (inside the transaction of `finishContractWithReview`, :123); contracts.milestones.service.ts:379 (transaction :317); proposals.review.service.ts:208 (`markProposalViewed` has no transaction: open a short one around the guarded update and the enqueue); proposals.submission.service.ts:100 and :205 (inside the submit transactions :35, :135, before the Redis cache write fixed by item 31). Each site: `const queued = await enqueueNotification(tx, input)` inside, `await sendUnlessQueued(queued, input)` after commit. No response shape or status code changes.

**Tests:** repository integration on the real test DB: idempotent insert on `event_id`; two concurrent claims never return the same row (use `R/test/support/lock-holder.ts`); expired lease is reclaimed; guarded mark with a stale `attempts` changes nothing; retention. Service with a mocked `sendNotification`: published, failed with backoff times, tenth failure -> DEAD, disabled leaves the row. Per site contract tests: **a rolled-back business transaction leaves no outbox row** (the core property), a commit leaves exactly one row with the deterministic id, `shadow` sends directly and inserts, `off` inserts nothing; architecture tests pass with the new module and layer entry; one real-broker integration test: a row relayed twice yields one `notifications` row. Contracts and proposals sites need the Tier 2 full suite and an Opus-model reviewer pass.
**Mutation checks (ordering-sensitive):** move one enqueue after the commit and see the rollback test fail; drop the `attempts` guard and see the stale-mark test fail; drop `SKIP LOCKED` and see the concurrent-claim test fail.
**DoD:** all of the above; ADR 0029 (options: relay in-process poll vs `LISTEN/NOTIFY` vs CDC, why in-module, flag semantics, retention); update ADR 0024 (the 8 kinds now optionally covered) and 0004 (header trace context); `api/AGENTS.md` Rules line listing kinds no longer "lost on outage" when mode is `on`; module count 16 -> 17 in docs. openapi hash unchanged.
**Reverse:** set `shadow` or `off` only after `outbox.pending` is 0 (otherwise rows wait until the relay returns); revert the commit; the table stays and a later migration drops it (never edit `0011`). **Risk:** medium (touches contracts and proposals services; notifications arrive up to about 1 s later in `on`; table growth if the relay is down, covered by the lag log).

## Part 4. Rules that keep the project healthy while it grows

**Introducing a pattern**

- One pattern per branch and per ADR; one concern per commit (AGENTS.md). The ADR is written in the same branch with: label (needed | adopted for learning), problem or learning goal, options considered, flag name and values, rollback, the measured signal, the removal signals below.
- Order inside a pattern: measure (metric or log exists) -> shadow or flag off -> behavior on -> remove the flag two sessions after it has been default-on and quiet. Flags that outlive that become debt and are listed in the report.
- Default is `off`. A pattern that changes behavior needs a `shadow` or dual-run step when it is reversible that way (outbox, idempotency, inbox).
- Complexity budget: at most two patterns in the "observing" state (flag not yet removed) at the same time, and never two that touch the payout or contract money paths in one week. Business features have priority: if a feature edits a module a pattern branch touches, the feature lands first and the pattern rebases.
- Never combine a pattern with a frontend batch or a wave-1 style bugfix in one session.

**What must stay true**

- Layer map, one owner per table, read allowlist, `boundary-exceptions.ts = []`, SQL only in repositories, services open transactions but import no drizzle helpers (ADR 0013-0017). A new module or layer entry updates the layer test, `docs/architecture.md` and `docs/adding-an-api-module.md` references in the same branch.
- Contract surface: routes or schemas changed -> `openapi:generate`, api-client `generate`, `sha256sum docs/api/openapi.json` before and after; items that must not change it say "unchanged" and the check proves it; frontend-visible code or status changes update `docs/frontend-integration-notes.md`.
- Money path (payouts, contracts, connects, refunds): Tier 2, mutation checks, an Opus-level review pass, tests that write PAID rows in `payoutTotalsFiles`, no pattern that retries a Stripe create without a stable key, and the checkout metadata id rule (D-1).
- Reliability invariants: Redis loss never changes an authorization result or a 2xx into a 500 (wave 1 31); RabbitMQ stays optional; every external call has a timeout; every retry is on an idempotent policy.
- Migrations: append-only, `/db-change`, local Docker only. Dependencies: owner approval, `minimumReleaseAge` untouched, versions pinned, `catalog:` only for shared ones.
- Performance guard: after Track 1, any pattern touching the request path compares the load baseline before and after (accept at most +10% p95 per stage, otherwise the ADR explains it).

**Signals to remove a pattern (each ADR copies the relevant ones with its own numbers)**

- Never exercised: a breaker that never opens, a retry that never retries, a cache with hit rate under 20%, a relay queue that is always empty, for 60 days of real use or three full test cycles.
- Costly: p95 regression above 10% against the baseline attributed to it, flaky tests traced to it twice, more than 15 minutes added to CI, or a session in four spent maintaining it.
- Harmful: it caused an incident or duplicate effect, or its failure mode is worse than the problem (for example a breaker open on a healthy dependency).
- Abandoned dependency: no release in 12 months or an unresolved security advisory it cannot upgrade past.
- Learning done and not needed: label "adopted for learning" and the goal reached; keep it only if it is cheap and flagged off, else remove. "Needed" patterns are removed only when the need disappears.
- Removal procedure: new ADR marks the old one superseded; flag off for a week; one commit removes code and tests; the owner deletes the files (agents list them under FILES FOR ME TO DELETE); tables are dropped by a new migration, never by editing an applied one.
