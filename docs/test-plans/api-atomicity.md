# Test plan: Stage 5c atomic meeting end and milestone double approval

## Scope

- `services/api/src/modules/meetings/meetings.service.ts`: `endMeetingByRoomName` now ends the meeting with one guarded `UPDATE ... WHERE provider_room_name = $room AND status = 'ACTIVE' RETURNING`, posts the `MEETING_ENDED` system message in the same transaction (via `postSystemEventMessage` with `{ executor: transaction }`, `src/database/db-executor.ts`), and emits the socket/SSE event only after commit. An emit failure is logged (`task.meeting.emit_failed`) and does not fail the end.
- `services/api/src/modules/meetings/meetings.controller.ts`: Daily webhook claim (`webhook:daily:<event id>`), claim released on error.
- `services/api/src/modules/contracts/services/contracts.milestones.service.ts`: `reviewContractMilestone` now updates the milestone with `WHERE id AND status = 'ACTIVE' AND payment_requested_at IS NOT NULL RETURNING`; no row means 409 "This milestone is not awaiting review."; a `23505` on `earning_history_milestone_id_unique` (also found through `cause`) maps to the same 409 and rolls back.

Use only the `_test` database (`src/test/setup/setup.ts` guards) and Stripe/Daily test or mocked data. Never use or print the real `.env`. Do not run any `db:*` script or start the API against the dev database for the automated part. The manual scenarios in section 2 need a running API and must only be run against a dev database that the user has already migrated (migration `0001`, see `api-payouts.md`).

Legend: U unit, I integration (real Postgres `_test`), E end to end / manual.

## Edge cases and negative cases

- Money: approval must produce one earning in integer cents with the gross unchanged and the fee rounded half-up on cents, so exact half-cent ties now round up where the old float code rounded down (ADR 0006; fee rate is "to confirm"); an agency milestone credits the agency, not the freelancer. Covered for both in CI; the 35-cent tie (fee 4, net 31) is covered in CI.
- Concurrency: only one of N parallel reviews wins; losers get 409 and must not send a notification (covered for 2 requests, not for N greater than 2).
- Rollback: a failure after the milestone update (earnings, conversation, notification rows) must roll back the status change; only the unique-violation path is tested explicitly.

## Not covered

- `startMeeting` atomicity, one ACTIVE meeting per conversation, and the other milestone and contract transitions (accept offer, submit, add milestone, finish): covered in `api-state-transitions.md` (ADR 0007).
- Real Daily signature verification and real Redis claim behavior across two API processes; real Stripe; process kill during the transaction; load beyond two parallel requests.
- The frontend behavior on 409 (no app calls the API yet per `docs/architecture.md`).

## Blocked on a decision

Fee, escrow and dispute rules remain "to confirm" in `docs/product.md`. This plan checks that the existing amounts are recorded exactly once, not that they are correct.
